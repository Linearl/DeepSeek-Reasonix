# fork 魔改特性实验化评估报告（任务 98，2026-09-13）

> **仓库内副本**：本文件于 2026-09-15 随 README 的 fork 说明一并传入仓库；此后以本仓库版本为准。

> **问题**：把哪些魔改特性做成实验特性，能减少后续合并上游的成本？
> **底表**：`release-notes/FORK-vs-upstream.md`（已于本日补登「开关 / 默认 / 承载文件」三列）
> **结论先行**：**真正适合实验化的只有「同一功能、两种做法」这一类，而这类我们基本已经做完了**（任务 60 / 81）。
> 其余魔改多数**不属于这个范畴**——做成开关既减不了 merge 成本，还会引入双路径的测试负担。

---

## 一、判断标准：什么才算「适合实验化」

把一条魔改做成实验特性，收益来自**关闭时能与上游行为逐条对齐**——于是 merge 时可以整段取上游，不必逐行判断。据此有三条硬条件：

| # | 条件 | 为什么 |
|---|---|---|
| ① | 能收敛成**一处开关控制** | 散在十几个文件的改动，开关本身就会冲突 |
| ② | 默认**关** | 默认开等于没关，merge 时仍要保 fork 侧 |
| ③ | **关闭时逐条行为与上游一致** | 这是全部收益的来源：可整段取上游 |

**反过来说，三类魔改天然不适合**：

- **A · 上游根本没有的功能**：关闭后没有"上游行为"可回落，代码是**多出来的**而不是**不同的**——冲突来自新增文件/新增分支，开关消除不了；
- **B · 正确性修复**：关掉等于把 bug 放回去，没人会关，也就没人会用它省 merge 成本；
- **C · 协议 / 数据格式差异**：两边互斥、无法共存，开关只能选边，不能让 merge 变简单。

## 三、merge 成本量化思路

光有定性判断不够，建议把 merge 成本变成可追踪的数字，才好判断某个动作（实验化 / 收敛 / 取上游）值不值。

**建议采集的三个指标**（每次追齐后记录）：

| 指标 | 采集方式 | 说明 |
|---|---|---|
| **冲突文件数** | `git merge --no-commit <upstream>` 后 `git diff --name-only --diff-filter=U \| wc -l` | 最直接的成本代理 |
| **冲突块数 / 行数** | `git diff --numstat --diff-filter=U` 求和 | 区分"文件多但都是小冲突"与"少数文件大段冲突" |
| **fork 独有文件数** | 与上游 tree 做双向比对（`git diff --stat <upstream> HEAD`） | 反映 A 类功能的体量 |

**已经有的基础设施**：`scripts/check-fork-*`（合并后完整性核对）+ 追齐时的"双向 tree 比对"步骤——把它们的输出按版本存档，就得到一条**随版本变化的历史曲线**。

**用它来回答的问题**：
- 某个魔改实验化之后，下几次追齐的冲突文件数有没有下降？（验证本报告的结论）
- Electron 迁移那一次追齐，冲突面相对历史是几倍？（决定迁移时机）

## 四、结论与建议

1. **不必再为"实验化"专门开工。** 最该实验化的两类（改已存在路径的功能、桌面侧新能力）分别由任务 60 / 81 覆盖，其余魔改落在 A / B / C 三类里——**开关减不了它们的 merge 成本**。

2. **真正能降本的是另外两件事**，建议优先：
   - **结构收敛**（任务 38 正在做）：把 fork 的重复状态并回上游已有的 store。这类改动**直接减少冲突面积**，比开关有效；
   - **测试守卫**（任务 97 已做两批）：让 fork 语义有断言保护，**避免下次 merge 被静默翻掉**——本次就发现状态栏默认值此前完全无守卫。

3. **merge 成本要量化**（第三节）。有了历史曲线，Electron 迁移的时机与"某个魔改值不值得实验化"都能用数据回答，而不是靠感觉。
