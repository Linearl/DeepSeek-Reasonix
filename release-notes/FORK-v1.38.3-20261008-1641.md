## 概览

本包合并第 12 版批 6 件（390/614/616/619/617+618），主题三个：**子代理消息通道**（运行中可给子代理发消息）、**启动提速**（tab 栏秒出）、**崩溃上报自有通道**（上游端点 503 下的完整替代）+ 视觉语义修正。

## 🚄 主线一：子代理运行中消息通道（任务 616）

子代理运行途中，现在可以直接给它发消息补充指令——不必等它跑完再重新派。

- 入口：子代理面板（CapsulePanel）新增发送框；
- 消息在消费前持久落盘（先写文件再投递），不因会话重启丢失；
- 开关：`experimental_subagent_messaging`，默认开启（实验特性，可在实验室关闭）。

## 🚄 主线二：启动 tab 恢复提速（任务 619）

修复启动时会话 tab 栏出现慢的问题（改前 ≥5.6 秒）：真根因是前端挂载时单次探测与恢复流程竞争。改后 tab 栏**毫秒级出现**，恢复过程以 ≤120ms 轮询平滑补齐。

## 🚄 主线三：崩溃上报自有通道 + 一键分析（任务 617+618）

上游崩溃上报端点不可用（503）背景下，fork 建立自有上报链路：

- **崩溃报告上传**走自有通道：失败记录日志（不再静默）、14 天 pending 老化清理；
- **一键分析**：诊断弹窗可复制 GitHub issue 骨架，或经三重前置探测后**自动新建 YOLO 会话**调用内置技能分析并提交 issue——崩溃从「贴日志人工问」变成「一键出根因报告」。

## 🧩 给下载用户的引导：用好内置的问题反馈闭环（重要）

本 fork 的 issue 分析技能做的是**源码级调研**（file:line 定位 + 分级修复建议），为让您的反馈直达根因，建议：

1. **把仓库 clone 到本地** —— 没有本地源码，技能只能提低质量 issue；有源码才能产出带根因的报告（执行成本走您自己的模型额度，不消耗维护者侧资源）；
2. **打开日志监控** —— 出问题时日志是定位前提（入口：设置 → 日志）；
3. **遇到问题用内置技能调查并发布 issue** —— 技能族：`gh-issue-submit`（提 issue）/ `github-issue-triage`（分诊）/ `research-to-issue`（调研转 issue）；崩溃场景直接用上面的**一键分析**。

> 说明：我们不做「低门槛无提炼」的反馈通道——不加清洗的 issue 是对维护者的污染（上游实测 151 条积压、65% 从无回应）。本链路的目标是「用户本地跑分析 → 带根因进 issue」。

## 🤝 主线四：zcode 协作体系 —— 本版本的最大加速器

本版本（及此前多个版本）的大量特性由 **zcode 协作体系** 开发落地：Reasonix 主对话作为协调中枢，把任务拆解派发给 **zcode**（一个好用的 coding harness）并行执行，再经合并线汇入主线、滚动出包装机验证。

- **为什么好用**：zcode 执行连续、任务完成质量高，大幅缩短了从立项到装机的周期——本版本 6 件特性中大部分由该体系交付；
- **协作面**：文件留言板派单/回板 + 转合并单 + bundle 预算棘轮报备的完整流水线；
- **同类借鉴致谢**：感谢 **mimocode** 让我们引入了跨会话协作模式，感谢 **GitHub Copilot** 让我们引入了 autopilot 模式——它们与 zcode 体系共同构成本 fork 的开发加速底座。
