# 回报格式（REPORT SCHEMA）· A2

> 所有子会话（开发 / 审计 / 合并）回报统一用本格式。管理会话派活时把本文件要点附进身份卡。

## 为什么要统一

管理会话的上下文是整批协作里**唯一的瓶颈资源**。它的上下文一胀，turn 就变长；turn 一变长，所有子会话的回信就排队滞后（§0.2 的反例实证：管理会话 100 轮 / 上下文 98.81%）。

所以回报的**格式与长度**不是小事，它直接决定批次能不能跑完。

## 四字段模板

```text
① 目标：<一句话，说明这次被派的是什么>
② 做了什么：<改动文件清单 + commit hash + 分支>
③ 验了什么：<跑了什么命令、看到什么结果>   ← 必填
④ 没验什么 / 阻塞点：<逐条，没有就写"无">
```

## 上限

- **开发 / 合并回报：正文 ≤ 30 行**
- **审计汇总：≤ 60 行**
- 超出部分 → **写成文件，给路径**。不要贴大段日志、不要贴文件原文。
- 给证据用 **路径 + 行号 + 关键几行**，不要整段复制。

## ③「验了什么」为什么是必填

worker 的自报天然乐观。实测中反复出现：

- "测试通过" —— 实际只跑了部分包
- "文件已更新" —— 实际编辑被拒、零写入
- "依赖已装" —— 实际装到了别的目录

**没写 ③ 的回报，按未完成处理，直接打回重报。** 这不是不信任，这是流程：③ 是唯一能让管理会话判断"能不能收货"的依据。

## ④「没验什么」为什么同样重要

只报验过的，等于默认其余都验过了。**必须显式说出边界**：

- 开发会话：「未跑全量 Go 测试，只跑了 `pkg/desktop`」
- 审计会话：「任务 240 的 UI 部分未审（缺渲染表快照）」
- 合并会话：「wt-B 的 bundle budget 数值我核了，但运行时行为未实测」

## 反例 vs 正例

**反例（会被打回）**：

```text
① 做完了。
② 改了 desktop 相关文件，测试通过。
```

问题：没 commit hash、没文件清单、③ 无具体命令与结果、④ 缺失。

**正例**：

```text
① 目标：给 Desktop 新增 `theme.accent` 配置键（任务 240）
② 做了什么：wt-240 分支 commit d5e86f423
   - desktop/config/render.go（+渲染行）
   - desktop/config/keys.go
   - desktop/frontend/types.ts、locales/zh-CN.json
③ 验了什么：
   - `go test ./desktop/...` → ok（含 TestDesktopRenderTableCoversEveryKey 绿）
   - `npx tsx desktop/frontend/__tests__/accent.ts` → 3 passed
④ 没验什么 / 阻塞点：
   - 未出包实测（按禁项不出包）
   - Tauri bridge 侧未改动，未验跨端行为
```
