# 承重结论清单（LOAD-BEARING CLAIMS）· B1

> 在 §5.1 任务分解时产出，随派活/审计消息一起下发。

## 什么是「承重结论」

**最终交付所依赖的结论。** 判据一句话：**这条如果错了，整批交付就是错的。**

不承重的例子：一处注释措辞、一个内部变量命名、日志文案。
承重的例子：

- 运行时契约（如「保存后重启仍生效」）
- 发版依据（如「渲染表覆盖了每个 key」——错了保存会被静默丢弃）
- 用户可见行为（如「切对话不再慢」）
- 跨线接口假设（如「A 线提供的函数签名是 X」）
- 装包内容（如「这个改动真的在产物里」）

## 模板

```markdown
# <批次> 承重结论清单

| # | 结论 | 归属线 | 若错的后果 | 需要的实证 |
|---|---|---|---|---|
| L1 | 保存后重启仍生效 | wt-240 | 用户配置丢失 | 装包实测（现象+日志） |
| L2 | 渲染表覆盖每个新 key | wt-240 | 保存静默丢弃 | `TestDesktopRenderTableCoversEveryKey` 绿 |
| L3 | A 线导出的 `ResolveAccent()` 签名为 (string, error) | wt-241 | 合并后编译失败 | 读源码 + `go build` |
| L4 | 改动确实在产物包里 | merge | 白出一版 | 祖先性 + 关键行逐字双证据 |
```

## 用法

1. **分解时产出**（§5.1），不用很长，5-10 条即可。
2. **派审计时附上**（§5.6）：清单内每条必须**真跑一遍 / 真读一遍**拿实证，不能只"看代码觉得对"。
3. **合并后复核**：标记为 `merge` 归属的条目在 §5.5 合并验证阶段核对。
4. **装包前复核**：`L*` 中依赖装机实测的，进 §5.7.0 验证文档，作为 👤 待人工项。

## 注意

- 这是**加码不是减码**：§5.6 的「全量审读」照旧执行，本清单只是让审计火力**优先**压在这些结论上。
- 不要把所有条目都标成承重——如果每条都承重，等于没有优先级。
- 「需要的实证」一栏必须写**可执行的核对动作**（跑什么命令 / 读什么产物），不能写"仔细检查"。
