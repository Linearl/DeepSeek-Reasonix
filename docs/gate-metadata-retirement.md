# 门禁元数据退役机制（tl1756）

> 2026-11-23 ｜ 机制文档（政策+判级标准+盘点流程）；逐轮盘点结果与拍板记录见 `docs/gate-metadata-audit台账.md`。
> 起源：`report/测试与QA验证体系不足分析-20261115.md` §3.4 / §3.6——fork-integrity 判例（57→847→856 只进不出）与 tsc 豁免（163 文件 226 条一次性登记）缺乏退役通道，豁免只进不出 = 真实回归被豁免掩埋 + 钉数线性涨（门禁自腐化）。

## 1. 适用范围（两份元数据）

| 源 | 位置 | 规模（2026-11-23 基点 baeb97db2f4 实测） | 判例形态 | 时间戳来源 |
|---|---|---|---|---|
| tsc 豁免 | `desktop/frontend/scripts/tsc-test-baseline.json` | 163 文件 / 226 对 file+错误码 | `entries: {文件: [TSxxxx]}` | 批量登记时点 `_meta.generated`（2026-10-10，任务 745）；后续逐条退役/补登以台账记录为准 |
| fork-integrity 判例 | `scripts/check-fork-integrity.mjs` `CHECKS` 数组 | 847 条（任务书口径 856 为任务创建时点数字；本数组持续增删） | `{feature, file, patterns[]}` grep 锚 | 每条登记行的 git blame 日期（锚点行最后改动 = 钉龄刷新点；重构换代改锚会刷新，语义见 §3） |

**不建逐条状态镜像库（SSOT 决策）**：两份元数据本身已是唯一事实源；再建一份「每条带 verdict 字段」的注册表会形成同语义双源，必有一套腐化（准则 8 / 设计原则）。因此时间戳取法如上表（机械可导出），复核结论只落在台账（逐轮增量的判定记录），不改门禁文件本体。

## 2. 退役条件（判级标准，两源各一套）

### 2.1 tsc 豁免条目（file::code）

| 判级 | 条件 | 动作 |
|---|---|---|
| 仍需要 | 全量 tsc 运行下该 file+code 仍有对应诊断 | 保留 |
| 可退役候选（强） | 该 file+code 的诊断已消失（欠账还清） | 列入候选清单 → 人工核对（排除增量缓存/解析遗漏）→ 拍板后从 baseline 删除该行 |
| 可退役候选（悬空） | 登记文件已不存在（改名/删除后条目悬空） | 同上；tl-1048 曾清过一条同类残留（227→226），此类历史上已实际发生过 |
| 待深验 | 未跑全量 tsc 时无法判定 | 机械盘点只标记，不下结论 |

说明：tsc 门禁本体（`tsc-test-gate.mjs`）在全量运行时**已自带** stale 提示（「基线中 N 对已无对应诊断，请人工核对后删除」）——本机制的增量是把这条一次性提示变成**周期台账+拍板闭环**，不改门禁判定逻辑。

### 2.2 fork-integrity 判例（feature+file+patterns）

| 判级 | 条件 | 动作 |
|---|---|---|
| 仍需要 | 门禁绿（文件与全部锚点在位）且功能仍是 fork 特有 | 保留 |
| 改锚（换代，非退役） | 锚点失效但功能仍在——锚点写法过时（历史判例：包80 字面钉随重构假红、tl1587 改锚、任务562 计数锚同步） | 更新 patterns 锚点；钉龄随 blame 自动刷新；**不得**借机退役 |
| 可退役候选 | 门禁红（文件或锚点缺失）且该 feature 确认已被**有意删除/替代**（需 handoff / release-notes / 任务台账佐证，非合并事故） | 列入候选清单 → 拍板后从 CHECKS 删除该行 |
| 真回归（非退役对象） | 门禁红且功能应存活 | 走 fork-integrity 门禁既有的恢复流程（从 origin commit 恢复），与本机制无关 |

**边界**：脚本只能把「门禁红」机械标出；「有意删除 vs 合并事故」的分辨永远人工——这是钉=「文件+子串 grep」机制的固有边界（tl1595 判例：钉绿≠行为对），退役判定同样不做自动化越权。

## 3. 时间戳与复核条件

- **每条都有时间戳**：tsc 源 = 批量登记日 `_meta.generated` + 台账中的逐轮复核记录；fork-integrity 源 = 登记行 git blame 日期（脚本每次盘点实时计算，不落镜像）。blame 语义 = 锚点行最后改动日，因此「改锚换代」会把钉龄清零——这是有意的：换代=人工看过一眼，复核责任重置。
- **复核条件**：每条候选必须带「为何可退役」的证据链（tsc：对应诊断消失的当次全量输出；fork-integrity：功能删除的佐证出处）。无证据不进候选清单。
- **钉龄审计**：钉龄 >180 天的判例进入半年一轮的人工抽样（与既有「实验室特性晋升观察」双周/半月节奏对齐，抽验「功能还活着吗」，不是抽验锚点——锚点绿否门禁每次合并在验）。

## 4. 盘点流程与节奏

1. **机械层（脚本全量，零人工）**：`node scripts/gate-metadata-audit.mjs [--with-tsc] [--json=<path>]`
   - tsc 源：文件存在性（悬空检测）；`--with-tsc` 时跑全量 tsc 并复用 `tsc-test-gate.mjs` 导出的 `parseDiagnostics/classify` 得出精确 stale 清单。
   - fork-integrity 源：复用 `CHECKS` 清单做存在性+锚点核对（判定逻辑与门禁同构但只读）、git blame 钉龄分桶、feature 标签内任务号（任务/task/tl/#PR）追溯抽取。
   - 本脚本**不是门禁**：不接 CI/Makefile，exit 0 只代表盘点跑通；候选清单是产出物，不阻断任何流程（验收约束「盘点不影响现有门禁执行」由此保证——两份门禁文件本体零改动）。
2. **人工判定层（只处理候选+抽样）**：候选通常远小于全量；逐条按 §2 判级，证据落台账。
3. **拍板层**：可退役清单只列不删；删除动作（改 baseline / 删 CHECKS 行）经用户拍板后由开发线执行，执行后脚本复跑应显示候选清零。
4. **节奏**：月度机械盘点（可挂心跳）；fork-integrity 全量人工判定仅在候选异常多或大合并后触发；钉龄抽样半年一轮。
5. **清零率**：`清零率 = 累计已退役条数 ÷（累计已退役 + 当前存量）`，逐轮记台账。首轮基线：tsc 0/226、fork-integrity 0/847（只盘点不删）。
6. **进侧随件登记纪律（20261128 批次拍板新增）**：tsc 基线「只减不增」只管出侧；**进侧（新增测试面类型诊断）必须随件登记**——新增/改动测试文件的件，验收清单加一条「有类型诊断→随件报数候拍板」，不许攒到基线刷红后集中补（tl1756 轮次2 实测：刷新后 3 天即漏进 23 条）。fork-integrity 新增锚同样随件登记（新增锚=既有惯例，此处明文化）。

## 5. 与既有机制的关系（竞品对照三问，宪法判据 8）

- **竞品/同型机制**：仓内已有两处同型——`check-known-failures.mjs` 的 RECOVERED→提示退役（§3.1 补强件）、`tsc-test-gate.mjs` 的 stale→人工核对提示。本机制 = 同一「登记-比对-提示退役」模式复用到另外两源，非新发明。
- **分叉收益**：tsc 源的 stale 信号已存在但停在「一次性 stdout 提示」；fork-integrity 源连信号都没有（只进不出）。收益证据：tl-1048 悬空清理、tl1587/任务562 锚换代、包80 字面钉假红——三类漂移均已实际发生。
- **保留成本**：一个只读脚本 + 一份台账；门禁本体零改动，无新的 CI 接线（接线候拍板，见 §7）。

## 6. non-goals

- 不批量删除任何豁免/判例（首轮只盘点列清单；退役动作候拍板）。
- 不改 `tsc-test-gate.mjs` / `check-fork-integrity.mjs` 判定逻辑本体（脚本只 import 其导出，不写回）。
- 不接 CI/Makefile（盘点是周期任务不是门禁；是否挂心跳候拍板）。
- 不建逐条 verdict 镜像库（§1 SSOT 决策）。
- 不合并两源为一份「统一豁免格式」（§3.1 红名单与两源分居是已知现状，统一格式是另一个任务的事）。

## 7. 候拍板（本轮不承诺）

- 心跳月度挂载 `gate-metadata-audit.mjs`（机械层全自动，产出增量报告）。
- fork-integrity 登记规范补「来源任务号必填」——现靠 feature 标签正则抽取，未知钉龄桶（无任务号）本轮实测见台账。
