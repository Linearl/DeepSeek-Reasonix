# 记忆向量层成本验证（bge-small-zh + ONNX Runtime Go 绑定）

- 任务：tl1351（P2）· 验证类件，只出报告候拍板，不实施到产品代码
- 日期：2026-11-08
- 实验目录：`expvec/`（worktree tl1351 内，独立 go.mod，不进主构建面）
- 原始数据：`expvec/bench-result.json`（程序自动写出）、`expvec/run-bench.log`、`expvec/run-retrieve.log`
- 结论速览：**条件值得**——推理与检索成本全是毫秒/MiB 级（不构成障碍），真正的成本在 CGO 构建链、约 107MiB 分发体积、约 +120MiB 常驻内存；收益在中文同义改写召回（关键词路实测有漏洞）

## 一、环境与口径

| 项 | 值 |
|---|---|
| CPU | AMD Ryzen AI 7 H 350（16 逻辑核），Windows 11 x64 |
| Go | `go version` 报 go1.26.9；实验二进制内 `runtime.Version()`=go1.26.3（两者不一致原因未深究，不影响结论） |
| C 工具链 | w64devkit v2.11.0（mingw-w64 gcc 16.2.0），CGO_ENABLED=1 |
| ONNX Runtime | 官方 dll 1.31.1（nuget 包 Microsoft.ML.OnnxRuntime，win-x64 native） |
| Go 绑定 | github.com/yalue/onnxruntime_go v1.38.0（要求 ORT API 31，与 dll 1.31.1 匹配） |
| 模型 | Xenova/bge-small-zh-v1.5 的 ONNX 转换版（HuggingFace），model.onnx 90.5MiB，fp32 |
| 词表 | vocab.txt 21128 条（BERT 中文词表，107KiB） |
| 推理配置 | ORT 默认 CPU EP、session 默认单线程、未调优；动态 shape，按批内最长 padding |
| pooling | last_hidden_state[:,0]（CLS）+ L2 normalize（BGE 官方语义，实测模型输出确认） |

**与任务书的口径差异（如实声明）**：任务书预期「768 维」，实测模型输出为 **512 维**——bge-small-zh-v1.5 的 hidden size 就是 512，768 是 bge-base 系列的规格。本报告按实测 512 维口径。

**tokenizer 口径（如实声明）**：Go 内自实现简化版中文 BERT tokenizer（lowercase + CJK 逐字切分 + 标点切分 + greedy wordpiece，约 150 行）。自洽性已验证：四档真实中文样本 UNK=0、编码→解码还原基本无损（详见 `expvec` selfcheck 输出）；**未**与 HuggingFace tokenizers 做 token id 级交叉验证（本机无 python+transformers 环境）。对成本/延迟结论无影响；对召回对照可能有微小偏差。

## 二、四项实测

### ① 模型加载耗时与常驻内存

| 阶段 | 读数 |
|---|---|
| dll 加载 + ORT 环境初始化 | 100.0 ms |
| session 创建（含 90MB 模型读盘+反序列化） | 199.0 ms |
| **合计冷加载** | **300.8 ms** |
| WorkingSet 增量（加载后，未推理） | **+120.0 MiB**（进程 7.1 → 127.1 MiB） |
| WorkingSet 增量（warmup 一次推理后） | +121.3 MiB（commit 122.7 MiB） |

结论：启动成本约 0.3s、常驻约 +120MiB。量级上「一次进程启动多花 0.3 秒」和「多占 ~120MiB」对桌面常驻产品可用，但不是零成本。

### ② 单条文本编码延迟（中文 100~500 字，预热 5 次后测 60 次）

| 长度档（实际字数 / tokens） | P50 | P95 | min / max |
|---|---|---|---|
| ~100 字（100 字 / 92 tok） | 8.14 ms | 10.12 ms | 7.21 / 11.05 |
| ~200 字（200 字 / 174 tok） | 14.02 ms | 16.75 ms | 11.53 / 17.93 |
| ~300 字（300 字 / 222 tok） | 17.51 ms | 21.55 ms | 14.95 / 23.40 |
| ~500 字（491 字 / 434 tok） | 39.97 ms | 63.32 ms | 33.85 / 87.95 |

结论：记忆条目典型长度（几十~三百字）下单条编码 **P50 8~18ms**，检索时 query 编码一次的开销完全可接受；500 字长条目 P95 抖动较大（63ms，受 CPU 频率/调度影响，样本方差大）。

### ③ 批量编码吞吐（100 条混合长度文本）

| 方式 | 耗时（中位） | 吞吐 |
|---|---|---|
| batch=100 一次推理 | 3247.7 ms | 30.8 条/s |
| 逐条串行 ×100 | 1752.6 ms | 57.1 条/s |

**反直觉结果与解释（实测非推测）**：batch 一次推理反而比串行慢一倍。原因是本实现按批内最长 padding——100 条混合 100~491 字的文本全部按 434 tokens 计算，而串行时每条按自身长度。推导（推演）：若按长度分桶 padding，batch 吞吐应高于串行；ORT session 默认单线程也压制了 batch 收益。**对集成方案的启示**：记忆写入是低频离线动作，逐条编码（57 条/s）已远超写入速率需求，无需为 batch 吞吐做工程投入。

### ④ 磁盘占用与检索延迟粗估（512 维）

| 项 | 实测/估算 |
|---|---|
| model.onnx | 90.5 MiB（fp32；官方有 int8 量化版可显著缩小，本次未测精度损失） |
| onnxruntime.dll | 16.5 MiB |
| vocab.txt | 107 KiB |
| **分发合计** | **约 107 MiB** |
| 向量索引体积 | **1.95 MiB / 千条**（float32×512 维裸存） |
| 暴力扫检索（1000 次均值） | N=100: 36us（单核）/ 26us（16 核）；N=500: 143/52us；N=2000: 450/112us；**N=5000: 784us 单核 / 202us 全核** |

结论：任务书问「几百条~几千条是否需要 Faiss」——**不需要**。5000 条全量暴力扫全核 0.2ms、单核 0.8ms，相对单条 query 编码的 8~18ms 可忽略；索引体积千条 2MiB 亦无需压缩。Faiss/ANN 在该量级纯属多余依赖，直接在 Go 里存裸向量+点积即可（本次已用纯 Go 循环实测）。

## 三、召回对照（向量 top5 vs 关键词 top5）

**实验设计**：模拟记忆库 100 条（`expvec/eval/corpus.tsv`，风格贴近本工作区真实记忆条目：环境/偏好/纪律/路径/故障历史），10 个中文 query（`expvec/eval/queries.txt`），混合精确词面型与同义改写型。向量路=余弦 top5；关键词路=整串子串命中(1.0) + 字符重合率×0.5 打分 top5（近似产品 grep 面）。**判定者：AI（本代理）人工判，主观性高，仅作方向性参考；语料与 query 同为本代理构造，存在同构造偏差**。样本量 10，不做统计显著性宣称。

| Query | 正确答案条目 | 向量路 | 关键词路 | 判定 |
|---|---|---|---|---|
| Q1 worktree 应该放在哪个目录 | m002 | top1 命中（sim 0.76） | top1 命中 | 平 |
| Q2 凭证、密钥这类东西存放在哪里 | m061/m074 | **top1 命中 m061** | m074 垫底第 5，m061 未进前 5（「凭证」vs「凭据」改写失败） | **向量胜** |
| Q3 删除文件之前要遵守什么规矩 | m013/m014/m076/m012 | 前 5 命中 4 条 | 前 5 命中 2 条 | **向量胜** |
| Q4 怎么把数据从这台电脑同步到另一台机器 | m071 | top1 命中（0.62） | m071 排第 5（「多机同步」无字面重叠） | **向量胜** |
| Q5 git 提交分支前要做哪些检查 | m042 | top1 跑偏（m003 被「git」字面带偏），top2 命中 | top1 即正确答案 | 关键词胜 |
| Q6 回复风格上用户有什么偏好 | m016 | 第 2 名，与 top1 几乎并列 | 第 4 名 | **向量胜（弱）** |
| Q7 遇到中文变成乱码是什么原因 | m080/m010 | top1/top2 双命中 | top1/top2 双命中 | 平 |
| Q8 新东西提交到 GitHub 之前需不需要先给人过目 | m048 | 第 3 名（前两名为 GitHub 字面噪声） | 并列 top1 | 关键词胜（弱） |
| Q9 从网上下模型太慢怎么办 | m004/m005 | top1 命中 m005，其余 4 条噪声 | m004+m005 双命中并列 top1 | 关键词胜（弱） |
| Q10 memory 里适合记什么内容 | m067/m092/m020 | 前 5 命中 3 条且分数领先 | 命中 2 条+英文词面噪声 | **向量胜** |

**汇总**：向量胜 5 / 关键词胜 3 / 平 2。定性规律：
- **同义改写型**（Q2 凭证↔凭据、Q3 删东西的规矩↔回收语义、Q4 电脑同步↔多机同步、Q6 偏好↔避免废话）：关键词路真实存在漏召回（Q2 正确答案直接出前 5），向量路稳定占优——这是向量层收益的核心证据。
- **带词面锚点的流程型**（Q5 git、Q8 提交、Q9 下载）：关键词路够用甚至更稳，向量路会被词面噪声（如 Q5 被「git」带偏到无关的 .git 条目）拉低首位精度。
- 精确词面型（Q1/Q7）两路都可靠。

## 四、集成改造量级推演（**推演**，非实测）

基于原型已验证的部分（推理/内存/检索为实测，集成工程量为估算）：

1. **检索侧（小）**：向量存储=每条记忆追加 2KB float32（1.95MiB/千条）；检索=query 编码（8~18ms）+暴力扫（<1ms）。几千条量级无需 Faiss/ANN（见②④实测）。
2. **代码量（中）**：推理封装原型约 240 行 Go（`expvec/bert.go`，DynamicAdvancedSession 封装）；tokenizer 简化版 150 行（集成时建议换 go-port 的 BERT tokenizer 库或用 HuggingFace exporter 内嵌，降低自维护面）；检索融合（关键词+向量双路合并排序）估 100~200 行；记忆写入异步编码钩子估 100 行内。
3. **构建链（主要成本）**：yalue/onnxruntime_go 是 **CGO 库**——产品当前 CGO_ENABLED=0 纯静态构建，引入后 Windows 构建链需要 mingw-w64 gcc（w64devkit 65MiB 工具链）、CI 需要加工具链与 CGO_CFLAGS/LDFLAGS 配置。这是本次验证实测出的硬门槛（CGO_ENABLED=0 下该库所有文件被构建约束排除，无法编译）。
4. **分发体积**：+107MiB（模型 fp32+dll）。可选降本（推演）：ONNX int8 量化版模型约可到 ~25MiB 级（onnx-community 提供 model_quantized 变体，精度损失未测）；内存常驻也可能随之下降。
5. **风险面**：CGO 引入的崩溃面（ORT native 层 panic 无法被 Go recover）；dll/模型分发与版本配对管理（yalue v1.38.0 必须配 ORT API 31，实测 1.19.2 dll 直接不可用）。

## 五、结论建议：**条件值得**

**支撑**：成本四项全部不是障碍量级——加载 0.3s、常驻 +120MiB、单条 8~18ms、千条索引 2MiB、5000 条检索 <1ms；收益方向真实存在——同义改写漏召回是关键词路的实测短板（Q2 最典型），向量路 10 query 判定 5 胜 3 负 2 平。

**条件（建议全部满足再立项实施）**：
1. 记忆库量级与检索痛点成立：实际记忆条目到数百条以上、且用户/会话确实因同义改写漏召回受过伤（本次对照语料为自构造，需以真实使用反馈复核）；
2. 接受 CGO 构建链：接受 Windows 构建链加 mingw-w64 工具链、CI 改造与 native 崩溃面；
3. 接受分发与内存成本：包体 +107MiB（或用 int8 量化降到 ~40MiB 级，需补测精度）、常驻 +120MiB；
4. 集成形态用**混合双路**而非替换：关键词路保留（词面锚点型 query 它更稳），向量路作兜底合并——避免 Q5/Q8/Q9 类词面场景的首位精度回退。

**不建议**：量级几百条以内就上 Faiss/ANN（实测暴力扫足够）；追求 batch 吞吐优化（写入侧逐条编码 57 条/s 已远超需求）。

## 附录 B：复现方法

```bash
cd expvec
# 依赖（版本配对敏感，见附录 A.4）
go get github.com/yalue/onnxruntime_go@v1.38.0
# dll + 头文件 + 导入库：nuget.org/api/v2/package/Microsoft.ML.OnnxRuntime/1.31.1
#   解包 runtimes/win-x64/native/{onnxruntime.dll,onnxruntime.lib}、build/native/include/
# gcc：w64devkit v2.11.0 解压后 bin/ 入 PATH
export PATH="<w64devkit>/bin:$PWD/models:$PATH"   # models 目录保证运行时找到 dll
export CC=gcc.exe CGO_ENABLED=1
export CGO_CFLAGS="-I<abs>/expvec/models/ort_sdk/build/native/include"
export CGO_LDFLAGS="-L<abs>/expvec/models/ort_sdk/runtimes/win-x64/native -lonnxruntime"
go build -o expvec.exe . && go run . selfcheck   # tokenizer 自洽
./expvec.exe bench      # 四项实测，读数写 bench-result.json
./expvec.exe retrieve   # 10 query 召回对照，全文输出见 run-retrieve.log
```

主构建面隔离验证：expvec 为独立 go.mod（嵌套 module），主仓 `go build ./...` 实测通过（GO 不进入子 module），产品代码零改动。
