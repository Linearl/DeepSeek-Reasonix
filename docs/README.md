# docs/ 目录布局规范（tl1824 起）

本目录是随应用构建嵌入的产品/工程文档权威源。一页讲清「什么放哪、放进来要守什么规矩」。

## 布局

| 位置 | 语义 | 约束 |
|------|------|------|
| `docs/*.md`（顶层） | **活文档**。随构建嵌入二进制（`docs/embed.go` 的 `//go:embed *.md`），供应用内文档检索（internal/productdocs） | 中文版与英文版同目录配对（`FOO.md` + `FOO.zh-CN.md` 或 `FOO_ZH.md` 旧例）；顶层文件即承诺「活」：有人读、有人维护 |
| `docs/superpowers/{plans,audits,specs}/` | 设计过程文档（方案/审计/规格） | 嵌套路径**不进**二进制嵌入；机制被取代的篇目移 `_archive/`，未取代的留原地 |
| `docs/_archive/` | **归档区**。失效文档（机制被取代、场景不存在、上游遗留站点副本） | 只移不删；git mv 保历史；详见下方归档纪律 |
| `docs/_archive/site/` | 上游遗留 Astro 官网站点副本（tl1824 归档，fork 不部署不维护） | 与本目录其余文档无链接往来；部署/分工说明见 `docs-site/README.md` |

## 归档纪律（tl1824 定版）

1. **只移不删**：`git mv` 进 `_archive/`，文件内容不改（历史由 git 承载）。
2. **移前核引用**：对每个待归档文件全仓 grep 文件名/相对链接引用（md 链接、代码引用、CI 引用、脚本清单）。有活引用的，先把引用断链改指新路径或注明归档，再动文件——归档不得制造新断链。
3. **双向修链**：指向归档文件的入链改写为新路径（并标注归档）；归档文件指向存活文档的出链补 `../` 相对前缀。
4. **扫描面豁免**：`docs/_archive/**` 不在公共契约扫描面内（`scripts/check-single-release-public-contract.mjs` 已显式排除），也不进二进制嵌入；如某脚本维护了以这些文件为键的例外清单，随移动同步更新路径或删条目。
5. **禁止断头引用**：归档后 `internal/` 代码中如仍残留以文件名为键的分支（如 productdocs 的 audience 标签），属 inert dead 分支，可留待 Go 线清理，但须在归档提交信息里申报。

## 与 docs-site/ 的分工

`docs/` 是**仓库内**的工程/产品文档源（顶层活文档随构建嵌入二进制）；`docs-site/` 是**对外** GitHub Pages 产品文档站（零依赖构建，见其 README）。对用户可见的产品文档以 docs-site 为发布面；对开发者/维护者的工程文档留在本目录。两站（本目录 `_archive/site` 与 `docs-site`）分工详见 `docs-site/README.md`「与 site/ 的分工」一节。
