# 「中断的工具需要核实」机制调研：全貌 / 溯源 / 竞品 / 移除影响 / 补位方案

**TL;DR（结论先行）**

1. **机制不是 fork 原创**：上游 esengine/DeepSeek-Reasonix 2026-09-10 引入（`8dda3994b`），fork 2026-09-14 移植（task 64，`b299a9e5a`）。上游动机原文防三件事：意图被当执行、不确定效果跨重启/历史改写丢失、无inspectable 恢复动作——核心是**防重复执行**与**防证据丢失**，不是防单次副作用本身。
2. **「只有新输入生效」有明确代码根因**：全部自动清除器（433 白名单结算、107 host 验证、435 重启结算）都住在 turn 执行管线/重启恢复链里；面板三按钮路径只有 inspect（只登记）和 confirm（可清，但被 inspect-first + `ErrTurnRunning` 门禁卡住），**reject 在设计上就不清除**（文案自认「继续阻止后续写入」）。切走切回只是重新 GET 快照，无任何结算逻辑。
3. **竞品均无逐条人工核实**：Codex 落一条模型可见「可能部分执行」标记 + 自动续轮；OpenCode/mimo-code 把在途工具标 `interrupted:true` 后仅记日志退出。主流方案=「标记不确定交模型下轮处理」，无一人拦写。
4. **fork 自己在 20 天内 6+ 次收敛性修复该机制的代价**（107→299→433→435→406→上游 #11386），方向一致：不断缩小拦截面。豁免面已覆盖 auto/yolo/autopilot/unattended 全部无人值守姿态；**attended ask 是唯一保留硬栅栏的场景**——正是用户实测卡住的场景。
5. **推荐：先修体验（a1 白名单结算前移 + a2 reject 语义改「解除写屏障留审计」），方向定「按可逆性分档豁免」（d），不整机制移除**——真风险场景（写类 bash 重复执行、压缩丢证据）仍有保护价值，且文件写已有 WriteVerifier 后置条件全覆盖、面板栅栏在那里的信息增量近零。

## 1. ① 机制全貌

### 1.1 两层数据结构

| 层 | 载体 | 谁消费 | 证据 |
|---|---|---|---|
| **A 层：durable 回执** | `provider.ToolCallRecord`（identity/session/turn/attempt、幂等键、状态机、resolution），挂在 `Message.ToolCalls[].Recovery`，provider-excluded（不进模型 wire） | 面板 `calls`、写栅栏、压缩保留 | `internal/provider/tool_recovery.go:36-53`；状态枚举 9 值 `:12-22` |
| **B 层：prompt-tail 交接** | `InterruptedTurnRecovery`（completed/unknown/not_started 分类事实块），LocalOnly 消息，注入下一轮模型上下文 | 模型（`<interrupted-turn-recovery>` 块）、面板 `silent` 标志 | `provider/tool_recovery.go:108-135`；注入 `internal/agent/interrupted_recovery.go:54-127`；`run_loop.go:164` |

### 1.2 触发条件（哪些中断路径产生核实项）

1. **执行期中断**（用户停止 / 超时）：`finishToolRecovery` 把 `context.Canceled/DeadlineExceeded` 映射为 `ToolRunUnknown`（`internal/agent/tool_recovery_barrier.go:64-72`），非只读的 unknown 记录即 unresolved；显式失败为 `failed`，但**非只读 + `effect_unknown` 的 failed 同样算 unresolved**（`tool_recovery_records.go:400-405` `unresolvedToolRecord`）。批量收尾在 `execute_batch.go:235`。
2. **强退/崩溃**：进程内无收尾，但 `beginToolRecovery` 在权限校验后就把 `started` 回执经 `RecoveryCheckpoint` 事件持久化（`tool_recovery_records.go:277-297`），重启后 reload 按 unresolved 处理——设计文档明说「已开始但未确认结果的调用仍为未知」（`docs/TOOL_RECOVERY.zh-CN.md:14-16`）。**用户实测强退后弹 `bash · 结果尚未确认` 即此路径**。
3. **silent 中断**：turn 结束时无任何可见输出 → `SilentInterruption`（`internal/control/recovery_status.go:8-57`），面板只出「继续任务」按钮（`ToolRecoveryPanel.tsx:84`）。

面板行文案来源：`snapshot.calls` = `executor.PendingToolRecovery()`（`internal/control/tool_recovery.go:34-50`），前端渲染 `{tool} · 结果尚未确认`（`desktop/frontend/src/components/ToolRecoveryPanel.tsx:68`）。面板挂载于 Transcript，每次条目变化重新探针（`Transcript.tsx:642`，`refreshKey={items.length}`）。

### 1.3 栅栏怎么拦

- **写栅栏**：`beginToolRecovery` 对「非只读新调用 × 存在 pending 非只读记录」硬停，报 `recovery_required: an earlier <tool> left an unconfirmed external effect...`，换 call ID 不能绕过（`tool_recovery_records.go:214-233`）。
- **run 尾栅栏**：`finishRunRecovery` 把 `ErrToolRecoveryRequired` join 进 run 错误（`tool_recovery_barrier.go:35-57`，调用点 `agent.go:1581`）。
- **历史改写保留**：压缩/rewind 时 unresolved 回执以 LocalOnly receipt 续命（`tool_recovery_records.go:409-428` `retainUnresolvedToolRecords`）。

### 1.4 全部真实清除点（6 个，逐一核对）

|---|---|---|---|---|

| 2 | `reject`（面板按钮） | 同上 | **不清除**：State 不动、只记 `Resolution=reject`，注释自认「Rejecting a retry does not prove the external effect absent」；zh 文案「未知效果仍被记录，并继续阻止后续写入」 | `tool_recovery_actions.go:93`；`zh.ts:21` |
| 3 | `host_verified_absent`（自动） | 写被拦时 `resolveHostVerifiableEffects` | 需工具实现 `EffectVerifier`——**仓库内零生产实现者**（仅接口 `internal/tool/recovery.go:17-21` + 测试 fake）→ **生产死路径** | `tool_recovery_records.go:465-515`；全仓 `) InspectEffect(` 实现者检索为空 |

### 1.5 用户实测三路径的代码走向（为何只有新输入生效）

- **三按钮**：`ResolveToolRecoveryForTab` → `Controller.ResolveToolRecovery` → agent。inspect 只登记 InspectionID；confirm 可清但须先 inspect 成功（`zh.ts:11`「请先点检查当前状态」）；reject 设计上不清（上表 #2）。且 controller 在 `running || finishing || rotating || closed` 时一票拒绝：**`ErrTurnRunning`，错误串恰为「turn already running」**（`internal/control/controller.go:74`；`control/tool_recovery.go:86-92`）→ 用户看到的报错即此处。前端在 `running` 时禁用全部按钮（`ToolRecoveryPanel.tsx:33,78-81`）。
- **切走切回**：仅 remount + 重新 `GetToolRecoveryForTab` 只读探针（`desktop/tool_recovery.go:20-38`；`ToolRecoveryPanel.tsx:17-30`），**不含任何结算逻辑**——记录不消，面板当然复现。
- **新输入开新 turn**：两段生效——(i) B 层交接被新用户轮**隐式消费**（反向扫描遇到 user-authored 消息即返回 nil，`interrupted_recovery.go:23-49`）→ `silent` 横幅消失、模型不再收到恢复块；(ii) 新 turn 执行任何工具时 `beginToolRecovery` 先跑 `resolveSideEffectFreeInterruptedCalls`（`tool_recovery_records.go:203`）→ 433 白名单内的遗留记录（**只读 bash 正是此类**）自动记「未生效」→ `PendingToolRecovery` 出清 → 面板下次探针为空。**两个自动清除器都只住在 turn 管线里，面板/查询路径一个都没有——这就是「只有新输入有效」的代码根因**。非白名单记录（写类 bash/MCP）新输入也不清，但那时写会被栅栏拦并指回面板。

### 1.6 豁免（toolRecoveryExempt）

- 判定：turn ctx 携带 `auto`/`yolo` 姿态（task 107）或 `unattended`（autopilot，task 107 P0-0/299）即豁免硬停与 run 尾 join；记录仍保留做事后审计（`tool_recovery_records.go:87-124`；`tool_recovery_barrier.go:27-50`）。
- 绑定面：`withRecoveryFenceBindings` 包住 controller 全部 turn 入口（`controller.go:1472-1486` + 调用点 1464/1487/1491/1500/1675、`turn_images.go:59/63`）；task 299 rework 专项「bind ALL orchestrator call sites, guard goes dynamic」（`d2426ebb2`，2026-09-24）。**豁免面完整性：turn 入口已全覆盖**。残余缺口一处：`RetryToolRecovery` 走 `ResolveToolRecovery` 的 ctx，不带 bindings（`control/tool_recovery.go:81-127`），但 retry 因 EffectVerifier 零实现者不可达，现状无实害。
- read-only 调用永不被拦（`tool_recovery_records.go:215` `p.readOnly` 条件）；task 283 把 readiness 卡的同族判定拓宽到 auto/yolo（`internal/agent/readiness_gate.go:28-39`，注释明说「the same family the tool-recovery fence honors」）。
- **attended ask 不豁免 = 设计意图**：107 提交说明原文「ask keeps the barrier」（`496b91830`）。

## 4. ④ 移除影响评估

前提事实：豁免面已覆盖**全部无人值守姿态**（auto/yolo/autopilot/unattended，见 1.6）；只读类已被 433 自动结清、计划内重启已被 435 结清。**「移除」的真实讨论面只剩 attended ask 姿态**。

### 4.1 真风险场景（机制有实际价值，移除即失去）

1. **写类 bash 重复执行**：`git push` / `pip install` / `curl -X POST` / `rm` 类中断后 unknown，盲目重跑=副作用双落。现有兜底：同名同参拒绝（`tool_recovery_records.go:272-273` user_confirmed 后重发同效果被拒）+ 模型提示「先只读核查再重试」（`interrupted_recovery.go:124`）；但**无参数级幂等**（bash 不实现 EffectVerifier，`TOOL_RECOVERY.zh-CN.md:52-54` 明说不承诺 exactly-once）。栅栏是这里唯一的硬闸。
2. **压缩/历史改写丢证据**：`retainUnresolvedToolRecords`（`tool_recovery_records.go:409-428`）让 unresolved 回执穿越 compaction——移除机制则连这份保障一起消失，模型对「可能已发生的外部效果」彻底失忆。
3. **MCP/网络工具**：无后置条件验证能力，unknown 是真实认知状态，无人可代答。

### 4.2 理论风险（既有机制已基本覆盖，栅栏信息增量小）

1. **文件写**：`WriteIntents + VerifyWrite` 后置条件五工具全覆盖（writeFile/editFile/multiEdit/notebookEdit/deleteRange，`internal/tool/builtin/write_recovery.go:90-118`）+ `recoverPreviousWrite/recoverPreviousUnknown` 模型级同名同参拦截（`internal/agent/write_recovery.go:89-98,151-165`）——同参数重复写已被拦，面板栅栏的额外价值只剩「强制人来点按钮」。
2. **ask 姿态的写**：中断的调用是**用户已批准过**的（approval 在案）；栅栏防的是「同一批准重复落地」，需要「批准→执行中断→下一写动作恰又触发」三连，发生率低。

### 4.3 本可无风险（已被既有机制清走）

只读工具与只读 bash（433）、ask 工具（433 白名单）、计划内重启（435）、无人值守全家（107/299）。**用户实测的 `bash · 结果尚未确认` 大概率属于 4.3 本不该亮面板、却因「白名单结算只住在 turn 管线」而亮起的类目**。

## 5. ⑤ 补位方法建议（低风险 → 架构级）

### 低风险档（修体验，与 X3 交互修复互补不冲突）

- **a1 白名单结算前移**：把 433 的 `resolveSideEffectFreeInterruptedCalls` 从「仅下一次 `beginToolRecovery`」提到**会话装载/boot 或快照读路径**（`Controller.ToolRecoverySnapshot` 或会话恢复点，一次性惰性结算）。改动小：复用既有判定函数（含 bash shellsafe fail-closed 语义），用户实测的 bash 只读类面板行**不依赖新输入即时消失**。
- **a2 reject 语义改为「解除写屏障 + 留审计」**：现状 reject 后记录继续 hard-block 写入（`zh.ts:21` 文案自认），用户按了「不重试」反而没有任何出口。改为：State 转 `not_started`（或新增 `unresolved_accepted` 态）+ `Resolution=reject` 留痕 + 非阻塞横幅；「防止未核实就继续写」的诉求由横幅+模型事实块承接。语义错配是用户「三按钮无效」感受的一半来源。
- **a3（X3 领域，仅记录）**：面板动作与 turn admission 解耦——inspect 是只读核查，不应被 `ErrTurnRunning`（`controller.go:74` + `control/tool_recovery.go:86-92`）一票拒绝；confirm/reject 至少应有排队或明确「turn 结束后生效」提示。

### 中档

- **b 降级为非阻塞事实 + 审计（Codex/OpenCode 模式）**：撤硬栅栏，保留 B 层 `outcome_unknown_tools` 事实块（已有「先检查再重试」指引）+ `tool_recovery` 只读工具 + 面板只读视图；重复执行由 `recoverPreviousWrite` 类同名同参拦截兜底。与主流对齐，代价是 4.1-1/2/3 的真风险失去硬闸。
