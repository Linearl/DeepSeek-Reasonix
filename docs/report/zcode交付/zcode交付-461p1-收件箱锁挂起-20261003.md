## 2. 修法（6 个切片 commit）

### 切片1 `67992fa55` — filelock 层统一加界（一次消灭全仓无界等待）

- 具名常量 `DefaultWaitTimeout = 5s`：`acquire()` 在调用方 ctx **无 deadline** 时
  统一套上（含 `context.Background()`），本地排队与跨进程重试两阶段都封顶；
  已有 deadline 的 ctx 尊重调用方预算。
- 重试循环新增 `case <-ctx.Done():`：`AcquireWithExternalTimeout` 的外部预算期
  （该阶段 fileCtx 基于 Background）调用方取消也**立即返回**——修复前「点停止
  无效」的第二处盲区。
- 设计原则入注释：**可用性 > 锁完整性，宁可超时失败不可无限挂**。

### 切片2 `55d4e8726` — collabinbox 主修复

- `Store.lock(ctx)` 改 `AcquireWithExternalTimeout(ctx, path, lockWaitTimeout)`，
  `lockWaitTimeout = 5s` 具名常量；失败包装
  `collab inbox lock busy (held by another window or process?), gave up waiting: %w`
  （含锁被占用语义，`errors.Is` 链保留）。
- `List/Chains/Dismiss/Undismiss/Decide/SetRetention/ApplyRetention/Settings/mutate/build`
  全方法贯通 ctx；`query_collab_mail` 工具不再丢弃请求 ctx；面板（Wails 无请求
  ctx、非可取消链）显式 Background + 内层 5s 兜底（注释说明）。
- 配套 `MailStore.lock(ctx)`、`History(ctx)`、`PruneInbox(ctx)`（唯一调用方即 collabinbox）。

## P10 根因（决定性证据闭环）

`inbox_idempotency_conflict` 不出自 P8 的投递层幂等，而出自**目标收件箱（sessioninbox）
的入队幂等层**：泵的内容键（from+thread+body-hash，`deliverOne`）在重发时相同，
但存档的信封指纹含逐条变化元数据（重发的新 msg id 参与渲染文本）→ 同 key 不同
hash → `ErrIdempotencyConflict`。而 `runCollabDelivery` 对入队失败的处置是
**「Not acked: retried next pass」+ 给发送方发「投递失败，将自动重试」状态通知**
——mail 每 5-6s 被重新 claim 重投、发送方被喂养重试 → 实测 16 组重复、同句×12、
173s。P8 的投递层幂等把「新开线程」的重发折叠在源头，但**带显式 thread_id 的
同线程重发**（worker 周期性回报类）不经投递层折叠、直达这个 conflict 死循环。

## P10 修法（`38fe568c6`）

- `collabAdmissionErr`：入队出错的分类点——`ErrIdempotencyConflict` 判为
  `errCollabDuplicateDelivery`（目标收件箱已持有同内容 = **重复已送达，不是失败**；
  存档信封与新信封只差逐份元数据，不差意图）。
- `runCollabDelivery`（决策点，同时识别 sentinel 与漏出的原始冲突）：重复投递
  **静默 ack 结算**——不发投递失败通知、不返回错误、下个泵周期无事可重投
  （循环断根）。真正的「同 key 不同内容」冲突仍走原失败路径（通知一次+保持
  pending），不误伤。
- 测试（重试方视角）：`TestIdempotencyConflictSettlesAsDuplicateDelivery`——
  首投成功 → 同线程同内容重发新行 → 入队注入 `ErrIdempotencyConflict` →
  断言 delivered=1/err=nil/零通知/传输层 unread=0（重投断根）。
- P10②（既有重复可一键清理）：由 P8-③ 折叠+MarkRead 承担，测试补强
  「全部已读 → badge 与传输层双口径归零」（`TestNineDuplicatesFold...` 扩展）。

## P11 根因与修法（`231e01082`）

- **实测**：`ListCollabMail failed err="collab inbox lock busy..."` ——P1 的 5s
  超时生效，但 `.collab-inbox.lock` 被长期占用 → 只读列表被写锁独占阻塞 → 面板空。
- **修法**（可用性 > 锁完整性，用户定调）：
  - List/Chains 读路径改 `lockRead`：**共享锁**（`AcquireMode ModeShared`，多读
    并行）+ `readLockWaitTimeout=1.5s` 短预算；
  - 拿不到锁 → **降级无锁直读**：`Snapshot.Degraded=true`、保留期跳过（降级读
    绝不改动任何状态）→ 面板有数据而非空；
  - 持有者诊断（P11①）：独占获取成功后把 `pid= held_since=` 写入 sidecar
    （`.collab-inbox.lock.holder`——锁文件字节区间被 LockFileEx 占住，第二句柄
    直写会失败，故用 sidecar）；写路径超时错误与桌面降级日志都指认
    `last holder: pid=…`。
  - 写路径（ApplyRetention/mutate/MarkRead/Dismiss/Decide/SetRetention）保持
    独占 + 5s 有界 + 取消即时（P1 语义不变）。

## P10/P11 遗留

- **信封指纹的逐份元数据**：冲突的源头是重发的 msg id 参与渲染文本。本件在消费侧
  兜住（冲突=重复已送达）；若要走出「幂等命中（Task 309 dedup proof line）」而非
  「冲突转成功」，需渲染文本剥离逐份元数据（改目标会话所见文本，涉及下游契约），
  建议另立切片评估。
- **持锁者定位是「最后持有者」**：sidecar 在释放后保留旧值（有放即有痕、无租约
  语义）。跨进程「当前持有者」需要租约心跳，成本高于收益，暂不做。
- **Chain 视图未降级标注**：Chains 也走 lockRead 降级，但 ChainSnapshot 无
  Degraded 字段（列表视图已够诊断），需要时补。
