## P6（追加派单）：长 turn 中 send 被拒自动降级

### 需求（任务清单 461 卡 P6 节）

超长 turn 进行中用户按 Enter → 原行为 `Send failed: turn already running`，消息发不出、提示与实际不符。修法四条：①send 收到 ErrTurnRunning → 自动降级（可注入→steer；否则排队到下一轮），不再弹 Send failed；②前端 turn 状态对齐权威信号；③UX 显示去向；④steer 也失败时排队持久化，消息不丢。与 P3 关系：P3=手动重发（失败后），P6=自动降级（失败前），互补不冲突。

### 位置与做法

| 内容 | 位置 |
|---|---|
| 降级拦截点 | `desktop/frontend/src/lib/useController.ts` `degradeRunningTurnSubmit`（rejectTurnSubmission 旁）；接入 `sendToTab` 的 promise 拒绝与同步 throw 两条路 |
| 降级链 | 能定界当前 turn → `EnqueueInboxSteerForTurn`（精确 turn 栅栏，防误注入轮替 turn）；否则 → `EnqueueInboxSteer`（会话级持久 steer）；steer 通道也拒绝 → `EnqueueInboxFollowup` 持久队列（④消息不丢）；全部失败才回落原 Send failed 面（P3 管辖）。入队的 `queued_followup` 由后端既有 inbox dispatch 循环（`internal/control/inbox_dispatch.go` NextQueued→TrySubmitInboxItem）在 turn 结束/空闲边界自动发出 |
| 降级 reducer | `desktop/frontend/src/lib/turnSubmissionFailure.ts` `reduceSubmitDegraded`（新动作 `submit_degraded`）：乐观气泡保持已投递、**绝不标 failed**；追加去向提示 info 通知 |
| 去向提示（③） | disposition=`steer_accepted` →「turn 正在运行：消息已作为补充指示加入当前任务」；否则 →「turn 正在运行：消息已排队，将在本轮结束后自动发出」（三语 `composer.degradedSteer`/`composer.degradedQueued`，带 258 的 `↪` 前缀并按 inboxItemId 与 agent 消费事件去重） |

## P7（追加派单）：三级终止交互

### 需求（七条，用户明确要求）

①第一次点「停止」=正常停止（≤1s 优雅退出）；②仍在跑则按钮变「强制停止」，第二次点击=进入 15s 宽限（倒计时「14s 后强制结束」，可随时再点直接跳即刻 kill）；③第三次点击=即刻强制 kill；④保底：无响应超 30s 自动宽限→即刻 kill；⑤kill 语义：turn ctx cancel 后工具仍未退出→强制终止（进程类杀进程树；goroutine 类记录+隔离，执行器不等它、立即释放 UI）；⑥hover 三档文案三语；⑦阈值可配置。

### 架构决策（放哪层，为什么）

状态机放**控制层**（`internal/control/stop_escalation.go`），不放前端：升级计时器（30s 保底/15s 宽限）必须由后端持有——UI 关闭/休眠时 kill 语义仍成立；kill 本质是控制层→执行器的信号。前端只做镜像（按钮三态/倒计时/hover 从 RuntimeStatus 读取 level+deadline），所有点击都调同一个升级入口，由控制层负责逐级推进——用户连点自然映射三级。

### 位置与做法

| 内容 | 位置 |
|---|---|
| L1/L2/L3 状态机 | `internal/control/stop_escalation.go`（新）：`CancelStop()` 每次点击升一级——L1=普通 cancel+30s 保底计时（④）；L2=开 15s 宽限倒计时（②）；L3/宽限中点击=即刻 force（②③）。turn 结束时状态归零（下次停止重新从 L1 开始） |

## P9（续派）：引导队列注入点扩展——工具间隙注入

### 需求

现状：用户消息在 turn 跑动时进「待处理引导」队列，只能等 turn 结束才作为下一条用户消息发出（长 turn 延迟小时级）。目标：同一队列，注入点从「turn 边界」扩展到「每次工具调用结束后」——Agent 循环在「工具执行完成→结果回灌」间隙检查队列并注入，补充指示感知延迟降到秒/分钟级。约束：①只在工具间隙注入；②与 P1 ctx/取消体系及 P7 stop 升级链兼容；③不改变队列语义与去重。

### 现状根因（读码结论）

系统里有两条通路：agent 内存 steer 队列（runToolLoop 每个 step 顶部已消费——steer_accepted 条目的注入点本来就是工具轮间隙）；持久 sessioninbox 队列的派发泵（`dispatchInboxOnce`）在 `c.running` 时**直接拒绝**并等 turn 结束的 kick——所有 **queued_followup 条目**（P6 降级回退、talk_to_session 排队、图片引导等）因此只能等 turn 边界。缺口 = 持久队列在工具间隙无人拉取。

### 位置与做法

| 内容 | 位置 |
|---|---|
| agent 工具间隙 hook | `internal/agent/agent.go` `toolRoundGap` 字段 + `SetToolRoundGapHook`；`internal/agent/run_loop.go` step 顶部（consumeSteer 之前）调用——hook 拉入的条目在**同一间隙**即被 consumeSteer 回灌，模型在下一轮请求上下文看到 |
| 控制层间隙派发 | `internal/control/inbox_dispatch.go` `bindAgentToolRoundGap`（构造器接线）+ `dispatchQueuedAtToolGap`：门组与 dispatchInboxOnce 一致（busy/pending-prompt/closed/rotating），task-221 合并组随行，投递走 `TrySteerInboxItem` 同一条路——接受=本间隙消费，拒绝=留在队列（语义/去重不变） |
| 活跃信号放宽 | `agent.SteerRunActive()`（新导出）；`TrySteerInboxItem` 的接受门从 `c.running` 放宽为 `c.running || executorRunActive`——orchestrator/synchronous 等不经 admission 的 turn 路径上「turn 活着」由执行器自身信号精确表达（bot 驱动的 turn 从此也能在工具间隙收到 steer，语义一致） |
| stop/cancel 兼容（约束②） | hook 在 run 协程的轮间隙触发，取消发生时循环在任何 ctx 检查点解卷、间隙停止触发；P7 的 force 只影响工具执行等待，不触碰该 hook；注入走既有 consumeSteer 通道，无新增 ctx 交互 |

### 验证（验收场景）

- `internal/control/inbox_tool_gap_test.go` 2 测试：**主验收**——mock 三轮长循环（gated 工具），round1 工具**运行中**入队 followup → 工具一结束的间隙拉入并回灌 → 断言 **round2 的模型请求上下文已含该消息**（≤1 个工具调用周期，捕获 provider.Request 逐轮取证）+ steer 队列排空；**暂停门**——inbox 暂停时间隙不注入（队列语义不变）。
- 回归：`internal/agent` Steer/ExecuteBatch/Partition/Parallel 族全绿（4.7s）；`internal/control` 全量 340s（唯一红=预存墙钟测试 TestOrdinaryChatTurnRunsPastTheOldRoundCeiling，基线同样红，勿修）；fork integrity 406/406（新增 2 条 P9 锚点）。
