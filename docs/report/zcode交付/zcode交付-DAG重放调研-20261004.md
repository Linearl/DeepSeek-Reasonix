# DAG 重放调研：内存占用 / 缓存效能 / 切 tab >10s 构成 / 竞品对照 / 优化方案

**TL;DR（结论先行）**

1. **今天的「切 tab >10s」主因已经不是 196 定案的「save 锁内全量重放」本身，而是它换了个形态**：save 侧图缓存修好后（本机日志已无慢重放行），一批**静默的全量解码调用**（LoadSession 族：搜索收集、话题标题、↑ 提示历史、时间叠层回退）共用同一把 save-path 互斥锁，对协作大会话（589 MiB 事件日志、9207 条消息）**约每分钟全量解码 ~2 次**（每次 ~25-30s、锁内、零日志）。用户切 tab 时 `SetActiveTab` 的同步快照在这把锁的队列里排 23-69s——实测今天 1 小时日志：96 次锁等待，**p50=28.1s，p90=54s，max=69.4s**，76/96 次 ≥10s。
2. **容量 12 是对的，但只救了 save 侧**：常驻会话交替保存实测 cap<K（K=同时活跃保存会话数）命中率 **0%**、cap≥K **100%**。但**load 路径根本不查这张缓存**——`loadSessionTranscript` 每次都从零重放，这才是今天的大头。
3. 首帧路径（187 尾窗）工作正常且与日志大小无关：257 MiB 日志 load-tail 仅 **1.8s**（全量重放 18.6s、峰值堆 723MB）。缓存的内存代价 ≈ **2.5× 日志字节/会话**（实测 257MB 日志 → 655MB 活跃图）。
4. 附带发现：**experimental_base_process=true 在本机握手失败循环**（`boot: base degraded ... baseproc: connection closed`，base.log 0 字节，fail-fast 回退 inline）——S1b 落地前该开关在本环境无收益。

## 1. A 量化

### 1.1 一次打开/重放的耗时与内存（探针实测）

| 日志 | 全量重放 wall | 重放峰值堆 | 活跃图（GC后） | 尾窗首帧（20MiB窗） | LoadSession 全量 | save 热缓存增量* | save 冷缓存全重放* |
|---|---|---|---|---|---|---|---|
| 32 MiB | 1.61s | 83 MB | 68 MB | 1.95s（峰 75MB） | 4.29s | 17.1s | 16.7s |
| 128 MiB | 6.10s | 344 MB | 297 MB | 2.37s（峰 162MB） | 16.1s | 71.0s | 83.7s |
| 257 MiB | 18.6s | 723 MB | 655 MB | 1.79s（峰 307MB） | 31.2s | 196.7s | 174.4s |

\* 探针环境数字，见第 0 节局限②；生产实测同一量级会话（589MiB）save 锁内工作量仅 0-3.6s（见 2.1）。

**可用的结论**：
- 全量重放 ≈ **72ms/MiB 线性**（589MiB ≈ 20-30s，与代码注释 467MiB≈19s 一致）；峰值堆 ≈ 2.8× 日志字节，活跃图 ≈ **2.5× 日志字节**。
- **尾窗首帧与总日志大小无关**（三个尺寸都 ~2s），187 修复有效；材质化（materialize）本身 0-8ms，成本全在解码。
- 内存上尾窗路径把峰值从 723MB 压到 307MB（257MiB 案例）。

### 1.2 dag_graph_cache_capacity 命中率（真实计数器）

计数器**已存在，无需新增**：`agent.SessionGraphCacheStats()`（hits/misses/evictions），且重放 ≥250ms 时 `session: dag state for save` Info 日志自带 `cache_hits/cache_misses/cache_evictions/cache_capacity`。读取方式：日志 grep，或临时诊断命令调 `SessionGraphCacheStats()`。

常驻会话交替保存实测（每 tab 打开时 LoadSession 一次，controller 常驻，之后轮流 Add+Save——即桌面真实模式）：

| 场景 | hits | misses | evictions | 命中率 | save p50 |
|---|---|---|---|---|---|
| K=6, cap=3 | 0 | 24 | 24 | **0%** | 2283ms |
| K=6, cap=6 | 24 | 0 | 0 | **100%** | 2104ms |
| K=6, cap=12 | 24 | 0 | 0 | 100% | 2058ms |
| K=12, cap=6 | 0 | 36 | 36 | **0%** | 2244ms |
| K=12, cap=12 | 36 | 0 | 0 | 100% | 2147ms |

（小日志下 miss 只加几十 ms 重放，所以 p50 差异小；大会话上 miss=每存多付 20-30s。）

### 1.3 12 够不够

- 判据：**cap ≥ 同时活跃保存的会话数** 即 100% 命中。用户原设 6 在 ≥7 个活跃 tab 时归零；12 覆盖到 12 个，超过 13 个活跃保存 tab 才会重新 thrash。
- 内存代价：每缓存一条 ≈ 2.5× 日志字节。若 12 条里有 3-4 个大会话（500MiB 级），驻留 ≈ 4-5GB——**cap=12 的真正风险不是 thrash 而是内存**。建议配套一个按字节总量封顶的进阶版（见 4.2-⑤）。
- 注意：这张缓存**只服务 save 路径**。load 路径（`loadSessionTranscript`）不 `sessionGraphCacheGet`，每次全新 `replaySessionDAG`——所以对今天的 >10s 问题，扩容帮不上（见第 2 节）。

## 2. B：切 tab >10s 耗时构成拆解（生产日志实证）

### 2.1 事实链（全部来自今日 desktop.log，可 grep 复现）

对象会话：协作主会话 `20260927-015341.569590500-mimo-api-mimo-v2.6-flash`，事件日志 **617,864,549 字节（589 MiB）**、9207-9211 条消息。

1. **锁等待分布**（`session: save-path lock waited`，阈值 250ms）：96 次，**p50=28.1s / p90=54.0s / max=69.4s**，≥10s 占 76 次。
2. **save 本体不慢**：`session: save phases` 显示锁内工作 `locked_total_ms`=0-3.8s（多数为 0——`snapshotUpToDate` 快路径直接跳过），无一行 `session: dag state for save`（≥250ms 才打）→ **save 侧已无慢重放，196fix2 缓存在生效**。
3. **锁在 save 间隙仍被长时间静默持有**（决定性时间轴，12:05-12:07 窗口）：
   - 12:05:17.836 一笔 save 结束；
   - 12:05:51.152 的等待者 wait=36.6s：刨去 12:05:17.8 前那笔 save 的尾段（3.3s），**12:05:18→12:05:51 有 ~33s 锁被非 save 操作持有，日志零痕迹**；
   - 12:06:24.031 的等待者 wait=66.1s（12:05:17.9 就开始排）——同窗口再叠加 ~30s 静默持有。
4. **静默持有者 = LoadSession 族全量解码**，量化证据：`image reference unresolved` WARN（`internal/agent/session_events.go:594` 解码时逐图告警）**~1500 条/分钟**，该会话 events 日志含 765 个 `reasonix-img://` 引用、imgpack 仅 45 个 blob → **每个不解析引用 ~720 个/次全量解码 → ≈2 次全量解码/分钟 ≈ save-path 锁 ~100% 占空比**。与 28-69s 等待队列完全自洽。
5. **tab 切换为什么撞上去**：`SetActiveTab` → `snapshotTabForAction` → `ctrl.Snapshot()` **同步**执行（desktop/tab_selection.go:67），排进上述队列 → 用户看到的「切 tab >10s」= 锁队列等待（23-69s），不是切换本身慢。

### 2.2 「切 tab 无计时埋点」疑点的核实结论

**埋点其实已相当全，唯独 load 路径是盲区**（这正是今天静默 30s 持锁能藏住的原因）：

| 路径 | 现状 |
|---|---|
| save 锁等待 | `session: save-path lock waited`（≥250ms WARN）✅ |
| save 锁内分相 | `session: save phases`（lock_wait/auth/heal/snap/probe/locked_total，Task 357）✅ |
| save 侧 DAG 重放 | `session: dag state for save`（extended/reason/分相/缓存计数，Task 196fix2）✅ |
| 前端切换分相 | `slow switch stage`（≥1s）/`hydrate stage`（≥100ms）/`history/<phase>`（Task 451，≥150ms）✅ |
| 打开会话 | `desktop: open session slow`（Task 298，≥2s 分相）✅ |
| history 切片 | `desktop: history slice timing`（Task 451，≥150ms 分相）✅ |
| **load 全量重放** | **无任何计时**——`loadSessionTranscript`/`LoadSession` 及其全部调用方静默 ❌ |
| **尾窗首帧** | `session: first-paint tail transcript`（仅尾窗分支有）⚠️ 全量回退分支无 |

### 2.3 静默全量解码调用点清单（今日嫌疑集合）

全部最终走 `loadSessionTranscript`（锁内全量重放，~72ms/MiB）：

| 调用点 | 用途 | 备注 |
|---|---|---|
| `desktop/history_search_collect.go:81` | 历史搜索逐候选 `agent.LoadSession` | 每次搜索一个大会话 = 一次 20-30s 锁内重放 |
| `desktop/tabs.go:5155`（topicTitleFromSession）| 话题标题升级检查 `LoadSessionUserMessages` | 标题源为 auto 时每次标题解析全量重放 |
| `desktop/app.go:5028`（collectEventLogUserPrompts）| ↑ 提示历史 | 有事件日志的会话每次查询全量重放 |
| `desktop/app.go:5671`（historyProviderMessagesWithPersistedTimes）| 时间叠层全量回退 | 已有 tail 变体（session_user_times_tail.go），此处是回退口 |
| `desktop/app.go:5743`（HistoryPageForTab idle 回退）| 历史页 v4 未命中时 `agent.LoadSession` | 前端已改走 HistorySliceForTab，旧入口仍是地雷 |

**2.4 埋点建议（先测量再下手，187 教训=别拿墙钟做断言）**

1. `loadSessionTranscript` 加与 `dag state for save` 同款的分相 Info（≥250ms 才打）：`path/bytes/replay_ms/nodes/msg_bytes`，一次阅读即可坐实「谁在每分钟解码」。
2. `lockSessionSavePath` 的 WARN 补「当前持有者」标记：持锁处打 `lock hold begin/end`（Debug 级）或直接在等待 WARN 里附上一个进程级 `atomic` 持锁者标签（loader/save/repair 三类即可）。
3. `image reference unresolved` 降噪：每会话每进程聚合一次（首次+计数），别按图刷屏；它今天恰好是定位功臣，但常态下每分钟 1500 条是纯噪音。
4. S1 观察：`experimental_base_process=true` 在本机 `base handshake: baseproc: connection closed` 失败循环（12:15/12:22/12:27 三轮，failures=5，base.log 0 字节）——底座子进程秒退，握手 fail-fast 回退 inline；S1b 接线前此开关在本环境无收益且有每次 boot 的握手代价，建议先修子进程启动再开。

## 3. C：优化方案分级

### 3.1 低风险（立即可做）

1. **把 save 移出切换关键路径**：`SetActiveTab` 的 `snapshotTabForAction` 改异步/后台化（快照失败已有 `reportTabSnapshotError` 通道，autosave 每 turn 兜底；纯 append 语义下晚几秒落盘风险可控）。**这一条直接消灭「切 tab 等锁队列」的用户感知**，改动集中在 tab_selection.go 一处。注意保留关闭/接管前的同步快照。
2. **ResidentExemptLimit=2 改可配**（`desktop/frontend/src/lib/transcriptStore.ts:458` 硬编码）：对齐 `dag_graph_cache_capacity` 的 0-默认/范围钳制模式即可；同时豁免数与 64MiB 字节预算的关系要在日志里保留（`noteResidentBudgetOver` 已有）。
3. **静默 loader 治理**（本轮 >10s 的直接病灶）：
   - history_search / topicTitle / ↑ 历史 改走 tail/read-model 变体（`session_user_times_tail.go` 已示范：同数据 tail 读几十 ms vs 全量 4s+）；
   - 这三类调用天然只需「用户消息子集/尾部」，不需要全图。
4. imgpack blob 缺失修复或一键重灌（720 个悬空引用既是每次全量解码的告警源，也说明图包丢数据）；WARN 聚合降噪（见 2.4-3）。
5. S1 底座：先修 `baseproc` 子进程秒退（base.log 空）再开 `experimental_base_process`；修好前回退 inline 的 fail-fast 路径保持。

### 3.2 中风险

1. **load 路径接图缓存**：`loadSessionTranscript` 在 probe 之后先 `sessionGraphCacheGet(logPath)`，命中且 generation/size 校验通过则免重放（校验逻辑 `dagStateForSave` 已有现成四件套：generation/sameLogPath/damaged/size）。收益：常驻 tab 的重开/重载从 20-30s → 毫秒级；代价：读路径与写路径共享同一把状态锁的正确性审查（state.mu 已就位）。
2. **REASONIX_DAG_FOLD_CHECKPOINT（308-O2 快照底座）评估开启**：机制已落地（checkpoint-first + 自播种），但自播种仅覆盖「head 带 compaction fold」的会话——大会话恰好是做过 compaction 的那批才受益；扩大播种面（定期 fold）是中风险改动，需先加命中/未命中计数（现有 `agent: dag checkpoint hit` 日志已有雏形）。
3. **save 分相埋点补全**：`save phases` 目前只覆盖 auth/heal/snap/probe，`planDAGWrite/digest/checkpoint/derived` 未分相；探针环境的 warm-save 线性增长（0.7s/MiB）与生产 3.5s 的矛盾需要这组数字裁决（一轮阅读即可，避免拿墙钟猜）。
4. 缓存按字节总量封顶：capacity 12 之上加「总驻留 ≤ N GB」的 LRU 维度（现只按条数），防 3-4 个大会话把进程推向 5GB+。

### 3.3 架构级（用户已定向要做：history 域迁底座 + 订阅模型）

**目标**：会话数据分片 + 订阅式切换——切 tab 不再「搬运/重建」任何大数据，只换订阅。

**可行拆解与前提**：

1. **写路径索引化（schema-3 演进）**：append 时同步写倒排/位置索引（display-index 已有 1.4MB/会话的先例，扩展为「消息→offset→turn」完整索引），读路径一律「索引定位 + 随机读」；全量重放只剩恢复/迁移两种场景。
   - 前提：CAS/租约单写协议不变（saveDAGLocked 的 revision ledger + lease）；索引写失败降级为现行为。
2. **读路径统一到 v4 投影**：HistorySliceForTab 已是正确形态（index→scan→event-log 三级降级 + 分相埋点）；把 2.3 清单里的静默 loader 全部迁到该入口，v4/SQLite 派的落地即「display-index 升级为真索引库」。
3. **订阅式切换**：前端 transcriptStore 已是 LRU 常驻 + 精准失效（`expectedRevision/expectedDigest`），缺的是后端推（turn 事件流已按 seq 回放，`TurnEventsForTab(afterSeq)` 就绪）——切换=对目标 tab 的事件流续订 + 一页首帧（tail 读），不再触发任何全量操作。
   - 前提：423「UI 首帧不等构建」+ 187 尾窗首帧已就位（本轮实测首帧路径 1.8-2.4s 恒定，已达「不等构建」）；active_tab_resident 豁免数可配后与字节预算联动。
4. **工作量粗估**（基于现有地基的增量，非从零）：schema-3 索引写路径 ~3-5 人日 + 双读迁移期 ~2-3 人日；loader 迁移 ~2 人日；订阅式切换前端 ~3-5 人日；回归面集中在 save/load 一致性与 fork 语义（DAG 的存在理由）。**真正要拍板的是「分支/分叉语义是否继续要求单文件全图」**——竞品全部用「分支=新文件」回避了重放（见第 4 节），若接受「fork 时一次性物化、之后线性 append」，重放可从热路径整体退役。

## 4. D：竞品对照（来源：本地源码副本 + 本机文件实证；不确定处标注）

| 产品 | 存储 | 「打开会话」策略 | 有无等价 DAG 重放 | 代价 |
|---|---|---|---|---|
| **Claude Code** | 每会话一个 JSONL（`~/.claude/projects/<slug>/<uuid>.jsonl`），线性 `parentUuid` 链，`isSidechain` 标子代理支线；`sessions-index.json` 摘要索引（sessionId/fileMtime/firstPrompt/messageCount/gitBranch）| 恢复=顺序读整个会话文件一遍；列表=读 index 不碰正文 | **无**（线性链+子链指针，无 fork 图） | 大会话全读一次（本机最大样本 8.1MB/2311 行，未见超大会话；官方未见公开的分窗机制文档——**不确定**其超长会话行为，公开资料仅确认「compact/摘要」机制存在） |
| **Codex CLI**（codex-rs，本仓副本）| rollout JSONL（append-only，`RolloutLine{timestamp,ordinal,item}`）+ 旧会话 zstd 后台压缩 + **SQLite 状态库**（state_db）+ session_index.jsonl | `get_rollout_history`=**整个文件顺序读**（异步 tokio，宽容解析错误）；元数据/序号用 **reverse JSONL scanner 从尾部倒读**（64KB chunk），不全读 | **无消息级 DAG**；`agent-graph-store` 只是线程父子拓扑（spawn 边），fork=独立 rollout 文件（`InitialHistory::Forked`）| 全读在恢复时一次性付出（异步不卡 UI）；压缩老会话换磁盘；SQLite 管发现/索引 |
| **OpenCode**（本仓副本）| 文件即库：每消息一个 `.json`（`storage/session/<sid>/message/<mid>.json`），effect-typed Storage 服务 | 打开=list 目录 + 按需读单个文件 | **无**（无单体日志，无重放概念） | 大量小文件的文件系统开销；无全量解码问题 |
| **MiMo Code**（本仓副本，OpenCode fork）| **已迁 SQLite**：`bun:sqlite`/node + drizzle，`session/message/part` 表 + 各类索引 | 打开=索引 SELECT | **无** | 迁移成本已付；读写走 SQL，天然免重放 |

**结论**：四家竞品**没有任何一家做「单文件消息级 DAG + 全量重放」**。Reasonix 的重放必要性来自 fork/分支共享同一份日志的语义；竞品一律用「分支=新文件/新会话（Codex Forked、Claude sidechain）」或「消息级寻址（OpenCode/MiMo）」把问题消解在写路径。这与第 3.3-4 的架构级方向互为印证：要么 fork 物化，要么索引寻址，二者都能让「全量重放」退出热路径。
