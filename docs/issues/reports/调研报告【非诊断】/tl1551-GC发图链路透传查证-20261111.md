## 一、调查面三问逐条回答

### ① GC 发图跨机传的是本机路径还是物化字节？

**物化字节，且协议上不存在可透传路径的字段。** 两侧读码：

GC 客户端（GrandCouncil，Android App，源码副本 `github-repo/GrandCouncil/`）：

- `app/src/main/kotlin/com/grandcouncil/remote/ui/sessions/SessionDetailScreen.kt:197-204`：Android 端用 `contentResolver.openInputStream(uri).readBytes()` 把图片读成字节，`Base64.encodeToString` 后调 `viewModel.attachImage(base64, mime)`。Android 的 `content://` URI 从不出设备。
- `app/src/main/kotlin/com/grandcouncil/remote/api/ReasonixApi.kt:44-46`：唯一上传通道 `POST /attachments`，body `{"data": <base64>, "mime": <string>}`。
- `app/src/main/kotlin/com/grandcouncil/remote/repository/SessionRepository.kt:131-141`：GC-22 注释自证设计意图——「上传图片拿 @ref（base64→ref）；内容物化在 PC 端（serve 存 workspace/.reasonix/attachments/）」。

宿主接收侧（reasonix serve，GC 经 servepool gateway `/p/<id>/attachments` 反代到达，`internal/servepool/gateway.go:309-374`）：

- `internal/serve/attachments.go:28-79`：handler 只解 `data`（base64）与 `mime` 两个字段；64 MiB 上限；`SaveImageBytesInRoot` 物化后返回相对 ref（`.reasonix/attachments/clipboard-<ts>-<seq>.png` 形态）。
- `internal/control/attachments.go:168-181`：`SaveImageBytesInRoot` 用 magic-byte 嗅探真实 mime（客户端声明的 mime 只做扩展名白名单交叉检查），文件名由服务端生成（`createAttachmentFileIn`），客户端完全无法影响落盘路径。

submit 引用：GC 拿到 ref 后拼进文本 `@<ref> <正文>` 走 `POST /submit {"input": ...}`（`SessionDetailViewModel.kt:495` `val withRef = st.attachmentRef?.let { "@$it $raw" } ?: raw`）。serve submit 的 body 只有 `input/format/action/recoveryId` 四个文本字段（`internal/serve/serve.go:930-935`），**没有结构化图片/路径字段**。

### ② 远程附件接收侧物化逻辑现状：缺失时显式失败还是静默降级？

**显式失败，两条消费链形态不同但都不是静默：**

- inbox 面（GC guided message / followup 主用面，经 gateway inboxGate 或 serve `/inbox/items`）：冻结时 `freezeInboxReferences` 把 `ResolveRefs` 的 errs 存进 `env.ReferenceErrors`（`internal/control/inbox_refs.go:24-26`）；投递前 `len(ReferenceErrors) > 0` 即阻断并给 blockReason（`internal/control/inbox.go:635-636`、`732-733`、`784-785`、`906-907` 四处；`inbox_refs.go:30-31`）。**ref 解析失败=消息不投递**，硬 fail-closed。
- serve submit 主链（GC 直接发消息面）：`runRefTurnWithResolverSync`（`internal/control/controller.go:2828-2841`）逐条 errs 发 `c.notice(e)`（Notice 事件，用户可见），并把含失败注记的 block 以 `Referenced context:` 前缀注入 turn。图片读取失败的注记是诚实化文案 `imageAttachmentFailedNote`（`internal/control/vision_images.go:75-77`）：「image attachment ... could not be attached as visual input ... **The image bytes are not in this turn.** Tell the user the attachment did not come through; **do not guess at the image content.**」——模型不会被误导去找一张不存在的图。

补充：`resolveInputImageCandidates`（`internal/control/refs.go:575-591`）对读不出 data URL 的候选是 best-effort skip，但它与 `ResolveRefs` 跑同一 input、同一失败根源，失败必然同时出现在上面的注记/Notice/ReferenceErrors 里，不构成静默通道。

### ③ fail-closed 缺口定位

**未发现缺口。** 纵深防线逐层核对：

| 层 | 机制 | 位置 |
|----|------|------|
| 协议面 | 上传只收 base64 字节，无路径字段 | `internal/serve/attachments.go:39-50` |
| 物化 | 服务端生成文件名+magic-byte 嗅探 | `internal/control/attachments.go:168-181` |
| 发送侧（GC） | 上传中禁发（fail-closed 注释原文）、失败显式报错且不产生 ref | `SessionDetailViewModel.kt:482-486`、`451-456` |
| ref 准入 | workspace 围栏：`workspaceRefPath`→`resolveAbsRef` 的 `filepath.Rel`+`filepath.IsLocal` 把 workspace 外绝对路径、`..` 逃逸全部拒收（进不了 ref 集合，保持纯文本，宿主不会去 open） | `internal/control/refs.go:530-541`、`813-839`、`1229-1250` |
| serve 加固 | scopedOnly 变体 `ResolveScopedRefs`（HTTP 面只认 workspace 内可解析路径） | `internal/control/refs.go:849-853` |
| 附件读取 | `cleanAttachmentPath`：绝对路径拒、强制 `.reasonix/attachments/` 前缀、`..` 拒；`rejectSymlinkComponents` 逐级拒 symlink；`readAttachmentImage` 不存在时显式报错 | `internal/control/attachments.go:595-641`、`539-593` |
| 大小/完整 | 1B-64MiB 界、open 后 SameFile 双校验、读后再校验 | `internal/control/attachments.go:561-587` |

关键推演（任务书担心的场景）：GC 恶意或错误地把本机路径（如 `/storage/emulated/0/DCIM/x.jpg` 或 `C:\Users\x\y.png`）塞进 `input` 的 `@token`——`detectRefsMode` 在 workspaceRoot 非空时（serve 面恒非空）只接受能解析到 workspace 内的 token，`filepath.IsLocal` 检查直接拒收；该 token 保持纯文本随消息进入，宿主**不会**对它做任何文件系统访问。既无「对端读不到文件」的正确性缺陷，也无路径穿越面。 even 若路径恰好撞上宿主 workspace 内同名相对路径，读的也是宿主 workspace 的真实文件，读不到/非图片同样走显式失败注记。

## 三、风险级别判定

**无正确性级缺陷，无 P1 实施必要。** zcode⭐22 清单担心的「GC 发图把本机路径传到对端、对端读不到文件」在现态架构下结构性不可能：协议没有路径字段（字节通道唯一），ref 全程由宿主物化签发，解析与读取双层围栏，失败显式呈现。与 tl1536（serve 二维码）、tl1532（submit 设备豁免）滚过的 serve 面现态一致。

## 五、残余观察（非缺口，不阻塞 cancel）

1. `inputImages`（`refs.go:562-570`）注释自称 best-effort skip，语义靠「同一失败必在 ResolveRefs 侧产出注记」这一耦合保证。若未来有人改动两处之一使耦合失效（如绕过 resolveRefs 直接 resolveInputImageCandidates），会退化成真静默降级——建议后续维护时保持两处同源，或把注记逻辑收敛到单点。
2. serve `/attachments` 的 ref 返回的是 workspace 相对路径，GC 直接拼 `@` 使用——若未来 workspace 迁移/多 workspace 场景，跨 workspace 的旧 ref 会走显式失败注记（读不到），行为正确但体验上可考虑「附件物化记录随会话走」的增强。不属本任务范围。
