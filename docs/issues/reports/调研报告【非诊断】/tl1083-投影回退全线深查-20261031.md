## 0. 结论先行（四句话）

1. **三实例同根成立**：根都在「多写者共享一份会话状态 + 失效校验靠 covered-prefix 哈希 + 兜底机制各有一道够不着的门槛」。投影失效只是症状，写者互踩才是病。
2. **「回退全量」在源码 tip 上已经被三代修复收窄**（719 尾窗 / tl1203 stale-serving / 912 滑窗永不全量），装机包62 已含这些；今天仍在发生的「全量回退感」来自**失效后重建永远失败**（401/超时/取消/内容再漂移），不是回退路径本身没修。
3. **8 轮压缩救不回的直接原因**：压缩的摘要请求自身打在「绑定模型的 3.7M token 输入」上——mimo key 401、换 glm 又被双写者竞速判 stale、心跳轮预算到点 cancel（attempt=8 cancelled）——四条死法轮流出现，唯一能落盘的 prune 只省 2K tokens；而唯一零模型的救命机制（任务1114 失效自动 Diet）对非 DAG 会话直接 return，该会话恰好已非 DAG。
4. **tl1183（真实 usage 触发）确认未进包**：装机 v1.38.3-20261031-1812=包62（e60f4d90d），tl1183 merge ccd78d346 在其后 7 个提交。装机的触发判断仍用本地估算（约 7% 低估），是「会话骑过触发线」的放大器，但**不是**今天循环的主因——3.7M/1M 差 3.7 倍，7% 口径差救不了它。

## 2. 三实例归因（真实文件+日志，file:line 级）

### 实例① 旧心跳会话（topic_20261021-162407 → 20261021-162413.432633800-session.*）

**症状**：3.7M/1M 超窗、压缩第 8 轮循环、每轮「本轮已中断」、events 53.4MB（历史峰值，现已被 diet/dagbak 拆存）。

**归因链**（每环都有现行证据，详见底稿 §1）：
1. canonical 2705 条≈3.7M tokens，sidecar projection_tokens=3,703,762≈source（v10，prune-only）。
2. 压缩摘要请求打在绑定模型：`context summary failed ... mimo-v2.6-flash ... HTTP 401 MIMO_API_KEY invalid or expired`（19:02/20:49/21:02 三次）——**压缩模型的 key 已死，fold 永远装不上**。
3. 换 glm 后手动 compact 又败：`compress: conversation changed while compression was running`（21:17）——**双写者竞速**（desktop tab 运行时 vs 心跳 serve 运行时 thinkbook14_YJC-18928，21:21:28 租约争夺记录在案）。
4. 后台重建 episode 全灭：`post-invalidation projection rebuild failed ... err="context deadline exceeded" rounds=2`（19:02/20:49/21:02）——5min×2 轮烧完放弃。
5. 心跳轮预算到点 cancel：turns.jsonl `compaction_done {attempt:8, pass:8, reason:"compaction was cancelled"}` → `turn_done {status:recovery_required, recovery:{reason:"silent_interruption"}}` = 用户看到的「本轮已中断」。
6. **触发条件归位**：T7 content_mismatch（desktop 侧 4 次告警，19:09-21:14，projection_version 4→9 每轮递增但校验永不过）+ T4 lineage（mimo→glm 一天内换 model）+ 双写者互踩。

8. **新增发现（挂起项）**：活体目录主 `.jsonl`+`.events.jsonl` 已缺失（三重验证），但日志仍显示 21:27「保存成功」（ms=7 ghost-save）。最后正常保存 05:30，删除窗口 09:00-15:10，删除者未定位（候选：会话保留期清理 ageDays / events_auto_rotation 门 / 外部删除）。**建议独立立项排查**：会话在写者不知情时被删文件，属数据完整性问题。

**症状**：recovery-3f03f3b8 分叉、「turn is not the active turn」、快照冲突。

**归因链**：

### 实例③ 切 tab 渲染卡（用户实测，关 tab 重开规避）

**归因链**：

## 3. 「压缩 8 轮救不回超窗会话」机制结论（两代逻辑分开推演）

**装机代（包62 及之前，旧触发逻辑）**：
- 触发：本地估算，约 7% 低估 → 触发偏晚。但实例①在 3.7M/1M，早已过任何线——**触发不是瓶颈**。
- 执行：ladder（pressure ≤2 次摘要）→ 摘要请求=把 3.7M token 全文喂给 1M 窗模型 → **摘要请求自身必越窗/超时**；chunked fallback（AllowChunkedFallback）在 pressure 触发下默认关闭（context_manager.go:104-107：ordinary pressure/overflow leave this false），只有显式策略才开。
- 失败处置链：401/stale/deadline → recordContextMaintenanceBlocked → prune-only receipt（实测 -2,088 tokens）→ 下一轮同一局面。
- 心跳轮 cancel 竞速：压缩是分钟级操作，心跳 20 分钟轮 + 每轮 cancel 检查 → `compaction was cancelled`（attempt=8 pass=8）→ turn recovery_required。**8 轮=8 个心跳轮各自从同一 3.7M 状态起跑、各自死于四选一的死法**，不是同一 turn 内递进 8 轮。
- 结论：装机代救不回=「摘要输入物理超窗 + 摘要模型 key 失效 + 双写者竞速 + 轮级 cancel」四因叠加，**与触发口径无关**。

**tl1183 代（未装机）**：
- 真实 usage 锚让触发时刻提前且判定精确（不再骑线），对「快到线的健康大会话」是有效预防。
- 对实例①形态（早已 3.7×、摘要必败、Diet 不可达）：**救不了**。tl1183 改的是「何时开始压」，不改「压不动时怎么办」。
- 真正缺的一环是：**失效×物理超窗×非 DAG** 形态的零模型自救。任务1114 已写了这个机制但把自己锁在 DAG 会话里（CAS 重写通路前置）；tl1227 DAG 退役之后，「非 DAG」从病态变成了普遍形态——**门槛与存储演进脱节**，这是机制级断言，不是个例观感。

## 4. recovery fork 的产生条件与 turn 归属错乱机制（要点）

- **产生条件**：保存时发现盘上 revision/digest 比写者 snapshot 新（SessionSnapshotConflictError）→ 三分流：2 分钟刹车窗内→adopt disk（不再 fork）；stale-prefix 类→adopt disk；其余→SaveRecoveryBranch（fork）。外加 external-removal（文件被删）与 shutdown 锁超时两源。
- **放大器**：刹车窗 per-controller，跨 controller 无共享刹车；fork 后新路径立即被绑定，双 controller 各自再竞写 → 连环 fork（今日 5 个）。
- **turn 错乱**：fork=换 sessionPath=桌面 runtime 换代（epoch bump）。换代前渲染的决策卡（Ask/审批/plan）携带旧 turnID/epoch，换代后栅栏必拒。症状瞬时、可自愈（新卡片用新 epoch），但用户观感是「按钮失灵」。

## 5. 方案概要（供协调线对齐后再立修复件；本件未改代码）

### 5.1 渲染卡根治（不靠关 tab）
- **最小**：resident 核鲜失败时降级走「尾部首绘+后台补史」（复用 LoadSessionTail/任务831③ 通道），替换现在的全量重载；仅对 messages>N 或 bytes>M 的会话生效，小会话零改动。
- **中等**：多写者会话的指纹改用「revision 段等价」而非全量 digest（尾部 revision 未动即可信缓存），减少 resident-stale 误杀；配合已有 tl1281 驱逐策略调参。
- **顺带**：切 tab 时若目标会话正处于 fallback/rebuild episode，先出 tail 视图占位，重建完成后无缝换页——避免「卡在重载」与「卡在重建」叠加。

### 5.2 超窗会话自救
- **P0（堵 Diet 门槛漏洞）**：任务1114 的 Diet 通路解锁非 DAG 形态——DAG 退役后 CAS 重写的前置条件改绑「存在可校验的物化转录」（tl1227 后的 checkpoint 形态），或为非 DAG 会话提供 checkpoint 兜底重写通路。实例①当场就能被这条救活。
- **P0（摘要输入解耦）**：压缩摘要请求不得直接喂超窗输入——pressure 触发下允许 chunked/tree-reduce（现默认 false）；或摘要前先本地截断到窗口内再总结。这是「越大越压不动」恶性循环的断根点（978 注释早已点名）。
- **P1（心跳轮与压缩的合约）**：轮级 cancel 不得打断进行中的压缩 episode（或压缩落地前 turn 不可 cancel）——「本轮已中断」×8 的直接来源；改后需保留用户手动 stop 的最高优先级。
- **P1（模型 key 健康联动）**：压缩用模型的 401 应触发「摘要换道」（切到会话当前可用模型做 summary），而不是让 fold 永远装不上；与 1190 的 recovery notice 同款式。
- **P2（tl1183 出包）**：已在 stable 等 63 包，滚合即可；出包后对「骑线晚触发」做一次前后对照。

### 5.3 recovery fork 预防
- **刹车窗全局化**：per-controller → per-session-file（跨 controller/进程共享最近 fork 时刻），2min→5min 起步；此为今日 5 连 fork 的直接拦截点。
- **fork 前先对账**：SaveRecoveryBranch 前先读盘上新 revision 做「差量合并尝试」（disk 只多不少时直接 adopt，避免分叉）——现有 adoptDiskSession 已覆盖 stale-prefix 类，把 diverged 类也先试一次段级合并。
- **换代后旧卡片作废重渲染**：epoch bump 时前端把该 tab 未决决策卡标记失效并给出「会话已恢复为新副本」提示，替代裸报错（turn is not the active turn 的体验面收口）。

### 5.4 挂起项（建议独立立项）
- 实例①主 `.jsonl` 无声消失+ghost-save：会话文件被删而写者无感知，数据完整性级问题，需定位删除者（保留期清理/rotation 门/外部删除三分方向）。
- max_output_tokens 设置校验（tl1083 A 项）：仍未实现，独立小件。

## 6. 验收建议（供后续修复件引用）

1. 构造「非 DAG+失效+3×超窗」会话 → 断言 Diet 通路触发且会话回到可发送态（§5.2-P0）。
2. 构造摘要模型 401 → 断言压缩换道到可用模型并落地 fold，而非 prune-only 循环。
3. 双写者同文件竞写 → 断言 10 分钟窗口内 recovery fork ≤1 个（全局刹车窗生效）。
4. 45MB 会话切 tab → 断言走 tail 首绘且 UI 主线程无 >500ms 阻塞段（frontend monitor stage 读数为证）。
5. 回归：健康小会话切 tab 零改动（快路径命中不变）；非超窗 400 恢复路径与改动前一致。

## 7. 通俗版一句话

三个毛病是一根藤上的：两个程序同时往同一份聊天记录里写字，谁写完都要喊「这页作废重念」，结果一份 370 万字的记录被迫每次从头念、念到嗓子哑（超窗报错）、想请人做摘要又发现摘要员的门禁卡过期（401）、刚要重新抄写就被下班铃打断（轮次取消）——而那台唯一不用开口求人的「本地碎纸机」（Diet）门口挂了块牌子「仅限老式装订本入场」，偏偏这本早换成新装订了。修法：给碎纸机换门牌、摘要先切碎再念、写字前先互相打个招呼、切页签时先只摊开最后一页。
