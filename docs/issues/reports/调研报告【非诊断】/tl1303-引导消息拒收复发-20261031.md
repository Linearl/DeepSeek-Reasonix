1. **本次不是 tl1291 上一轮的 write authority stale**：全程 desktop.log 零命中 "no longer writable"，admission_guard 的 write-authority 拒绝（internal/control/admission_guard.go:338、internal/control/session_write_authority.go:52）未触发。tl1291 修的是 fold-probe nil map 崩溃（提交 ea8a16d4a），与本次机制不同——**复发是新机制，不是旧病复发**。
2. **真实链路 = turn 被 ledger 写入失败连续打死 + 引导消息降级链把消息塞进一个垂死的 run**：
   - turn A（协调线正在跑的轮次）在 21:18:12–21:18:21 三次遭遇 `session snapshot conflicts with newer transcript`，每条 ToolDispatch/ToolResult 事件 append ledger 失败都直接触发 `owner.fail` 把 turn 判死；

## 三、报错链归因（file:line）

按消息流向：

1. **turn 打死点**：`internal/control/turn_events.go:234-245`（`turnEventDurableSink.EmitChecked`）——`persistAndPublish` 失败即 `slog.Error("controller: append turn event ledger", ...)` + **`s.owner.fail(err)`**；`fail` → `internal/control/turn_events.go:115-119` → `failTurnEventLedger`（`internal/control/turn_events.go:421-441`）：记 `turnEvents.err`、`c.canceling = true`、`c.cancel()`、`CancelAll()`。设计意图是「毒 WAL 立即取消 provider/prompt/process」——本次 transcript 分叉触发了它三次。
2. **前端降级链入口**：`desktop/frontend/src/lib/useController.ts:5022-5077`（`degradeRunningTurnSubmit`，任务461-P6）——仅当错误匹配 `/turn already running/i` 才降级；三级 fallback：`EnqueueInboxSteerForTurn` → `EnqueueInboxSteer` → `EnqueueInboxFollowup`。
3. **exact-turn 拒收点（协调线看到的报错）**：`desktop/inbox_app.go:227-229`（`EnqueueInboxSteerForTurn`）——`status.TurnID != turnID || !status.Running` → `turn %q is not the active turn for tab %q`。fork rebind 后 `RuntimeStatus().TurnID`（`internal/control/controller.go:2871-2888`，turnID 来自 ledger 的 `ActiveTurnID`，`internal/control/turn_events.go:382-389`）与前端缓存脱节 → **必拒**。
4. **吞错点**：`useController.ts:5037-5049`——`EnqueueInboxSteerForTurn` 抛错被 catch 进 `steerError`，只要 session 级 `EnqueueInboxSteer` 返回 receipt 且无 error 就当成功；"not the active turn" 这个信号本身（=没有可注入的活 turn）被丢弃。
5. **消息终点**：`internal/agent/agent.go:1061-1071`（`SteerItem`：`steerRunActive=true` 即入 `steerQueue` 返回 true）→ run 退出时 `internal/agent/agent.go:1233-1246`（`flushSteerQueue`）→ `RecordUnappliedSteer`（agent.go:1268+）：transcript 存档、**永不投给模型**（#7045 防陈旧指令），且不发前端可感知的 Notice。
6. **双事实源分裂（矛盾窗口）**：21:25:41 submit 见 running（controller `c.running`），21:26:10 tab 快照见 idle（ListTabs 投影）——`RuntimeStatus` 与 tab 投影是两条事实源，run 卡死/退出窗口内不一致。此分裂的全面排查归 tl1083。

**引导消息生效的两道闸**（本次都失效）：
- 入队闸：`internal/control/inbox_steer.go:111-236`（`trySteerInboxItem`）——`accepted = turnMatches && !closed && !rotating && (c.running || executorRunActive) && executor.SteerItem(...)`；
- 消费闸：tool-round gap 注入（`internal/control/inbox_dispatch.go:245-278` `dispatchQueuedAtToolGap`）+ turn 边界 pump。run 卡死则两闸全静默，且 accepted→生效之间**无任何监督与告警**。

## 四、与 recovery fork 交叉判定

**判定：同因交叉（因果），非纯并发。**

- 同因：fork 的触发错误与打死 turn 的错误是**同一条** `session snapshot conflicts with newer transcript`。时序上 append 失败（21:18:12-21）在前、fork 处置（21:18:31）在后（mode=rewrite）。
- 交叉机制：fork 后 `rebindTurnEvents`（turn_events.go:391+）把 ledger 换到新 sessionPath，`ActiveTurnID` 与前端 `resolveActiveTurnId` 的缓存（`desktop/frontend/src/lib/inboxSubmit.ts:7-17`，注释明确点名 recovery fork 回退场景）不再一致 → exact-turn steer 校验必拒 → 引导消息永远落到 session 级 steer 或 durable 队列，而 run 已死 → 沉没。
- 分叉本身的外因（「另一写盘者」是谁：第二 runtime/lease 争用/包62 回归）**不在本件下结论**，归 tl1083 深查件；本件只钉死「分叉 → 打死 turn + rebind 换代 → 引导消息拒收/沉没」这一段因果。

## 五、同类机制扫描（影响面）

按「不许浮于表面」纪律列同类，**修复范围待拍板**：

1. **所有走 `degradeRunningTurnSubmit` 的提交面**（普通消息/编辑重发/结构化提交，useController.ts 三处 `resolveActiveTurnId` 调用点 5041/5223/5286）——同样会在 fork/turn 换代后把消息塞进死 run。触发条件：run 卡死或 fork rebind 窗口内发消息。可见性：用户侧「发了没反应」。
2. **`append turn event ledger` 失败 → fail 的全部触发点**：任何持久化冲突（不止 transcript 分叉，还包括毒 WAL 等）都会立刻打死 turn。这是设计选择（fail-fast），但它与「引导消息已 accepted」组合后产生静默丢失。
3. **`flushSteerQueue` 的 unapplied 静默化**：所有「run 退出时未消费的 steer」都走这条路，无前端通知面。steer_accepted 与生效之间无监督（本件主坑）。
4. 19:03-19:12 ai-passport 三连 fork 的会话同样暴露在 1-3 的组合风险下（同包62 装机日）。

## 六、修复方案概要（候选，供另立修复件拍板）

**最小面（推荐先做）**：
1. **不吞 exact-turn 拒绝**：`degradeRunningTurnSubmit` 里 `EnqueueInboxSteerForTurn` 返回 "not the active turn" 时，视为「无可注入的活 turn」信号——跳过 session 级 steer（死 run 不会消费它），直接 `EnqueueInboxFollowup` 走 queued_followup（turn 边界 pump 会派发），并给用户「已排队，将在本轮结束后发出」的事实文案（复用 `composer.degradedQueued`）。
2. **unapplied 不再静默**：`flushSteerQueue`/`RecordUnappliedSteer` 时补发一条 Notice 事件（「引导消息未能注入本轮，已存档」），让前端引导 shelf 可感知、可重发。
3. **accepted→生效加监督**：steer_accepted 后 N 秒无 tool-round 注入且无输出，由 turn-watchdog 面报 frontend-log（新增观测点），让「发了没反应」可归因。

**中等面（建议并入 1083 主件）**：fork/rebind 后统一 `RuntimeStatus` 与 tab 投影的 running 事实源；「另一写盘者」根因查处。

**代价与风险**：候选 1 改变降级链行为（steer_accepted 变 queued_followup 的场合增多），需按「UI 变更对现有体验影响最小」给 notice 文案；候选 2 需避免 Notice 风暴（合并同类）；候选 3 纯观测无行为风险。

## 七、验收标准（修复件用）

1. 重放本件时序（fork rebind + run 已死 + 用户发引导消息）：消息**必达**（queued_followup 在下一 turn 边界派发），用户可见「已排队」事实文案，无「已加入当前任务」的假成功。
2. run 退出时存在未消费 steer：transcript 有 unapplied 存档 **且** 前端有 Notice。
3. desktop.log 中 `submit degraded to guidance queue ... disposition=` 与实际消费结果（steer 注入/queued 派发/unapplied 存档）三者可互相对账。
4. 「no longer writable」文案零回归（本件确认该链未被触及）。

## 八、通俗版一句话
