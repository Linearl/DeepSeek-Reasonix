## 一、竞品对照（纪律硬性：发明新机制前必做）

### 1.1 上游 DeepSeek-Reasonix（esengine）main-v2：**查无，如实标注**

- `git grep -l "package workflow" upstream/main-v2 -- "*.go"` **零命中**——上游没有 workflow 引擎包。fork 的 `internal/workflow` 是 685/686/934 三任务的 fork 自研件。
- 文件名级枚举 `git ls-tree -r upstream/main-v2 | grep -i workflow` 仅命中 `.github/workflows/*.yml`（CI 配置）与 `scripts/ci-workflow.test.mjs`，与运行时 workflow 引擎无关。
- 「studio」关键词全量内容级 grep（*.go/*.md）：仅 LM Studio（provider 名）与 Visual Studio Marketplace（VS Code 插件安装链接）两处引用——**上游不存在「studio workflow」功能面**。任务书所列「上游 studio workflow」在本上游仓库查无对应物，此处如实标注；若该词另有所指（上游其它仓库/分支），需出题方补充指向后再补查。
- 上游与「run 持久化」语义最接近的既有件是 **heartbeat run-history sidecar**（`desktop/heartbeat_store.go:38` "execution journal kept outside the main file"）——它属于 fork 与上游共有的心跳机制，已列入 §2 的继承源清单，不算 workflow 竞品。

### 1.2 zcode workflow（本地仓库副本 `github-repo/zcode`）：**有完整 run 持久化 + resume，双存储形态**

**存储形态 A——文件型 NodeWorkflowStore**（`apps/zcode-cli/packages/adapters/src/workflow/index.ts`）：

```
~/.zcode/cli/workflows/
├── index.json                  # 运行列表索引（WorkflowRunListItem 数组，upsert 更新）
├── definitions/                # workflow 定义 JSON（与 fork store.go 同构：一文档一文件）
└── runs/<runId>/
    ├── events.jsonl            # 追加式事件流（appendEvent → appendJsonLine）
    ├── graph.jsonl             # 追加式图记录
    ├── run.json                # 最新快照（writeSnapshot → 全量覆盖写 + upsertIndex）
    └── artifacts/…             # run 产物（report.md 等，按原扩展名落盘）
```

**存储形态 B——SQLite dwf journal**（`adapters/src/storage/session-store/repositories/dwf-journal.ts`）：`dwf_*` 表族（run/actor/node/event/artifact/settlement），`JournalStorePort` 同步仓储端口贴合 `node:sqlite` 的 DatabaseSync，落在 session db 内。

**run 状态机**（`contracts/src/workflow/index.ts:11-30`）：run 六态 `pending/running/paused/completed/failed/cancelled`；节点六态 `pending/active/completed/failed/skipped/cancelled`。

**resume 语义**（核心参照件）：

- 入口是独立工具 `ResumeWorkflowRun`（`core/src/tool/handlers/resume-workflow-run.ts`）：**只允许 `stopped` 态续跑**（stop reason `superseded` 除外）；`errored` run 必须走 `AmendWorkflow`（修正脚本后新 run 继承旧 run 已完成工作作为缓存，行内 `resumed_from` 属性记录溯源）；`completed` 无可续。
- 恢复算法 `reconcileWorkflowSnapshotForResume`（`core/src/workflow/lifecycle.ts:88-130`）：**非 active 节点状态一律保留；中断时处于 active 的节点重置回 pending（重跑）**；受影响 phase 与 activities 联动重置；随后 `continueRun` 从 pending 继续调度。resume 前先 `writeSnapshot(resumed)` 落修复后的快照，并 append 一条 `graph_updated` 事件说明修复了 stale active work。
- 用户主动停止的 run 带提示「The user stopped this workflow on purpose. Do not resume it with ResumeWorkflowRun…」（`runtime-task/notification.ts:266`）——**主动放弃 ≠ 可续跑**，这条语义值得继承。

### 1.3 fork 自身既有语义（「沿用既有存储语义不造新机制」的继承源清单）

| 既有件 | 形态 | 本设计继承点 |
|---|---|---|
| workflow 定义存储（store.go） | `WorkflowsDir` 一文档一 canonical JSON；tmp+rename 原子写；`list()` 枚举目录逐文件解析、**损坏文件跳过不炸目录**；dir 为空退化为内存 | 同目录同语义承载 run 快照；损坏跳过；空目录退化 |
| heartbeat run-history sidecar（desktop/heartbeat_sidecar.go，`heartbeat-tasks.runs.json`） | 侧车文件 + schemaVersion 前向保护（新版本 schema 拒写并提示升级）+ `maxRunHistory=20` 截断（mergeRunHistory 去重按时间保留最新 N 条）+ 两文件提交（sidecar 先写 staged、主配置为 commit marker、previous 代际回退） | schemaVersion 前向保护；终态历史条数上限语义（§7 的 100 上限同源） |
| `fileutil.AtomicWriteFile`（internal/fileutil/atomicwrite.go） | 带父目录 sync 的原子写，比 store.go 手写 tmp+rename 更强 | run.json 落盘直接用它，不再手写 tmp+rename |
| `agent` 子代理转录侧车（task.go MarkRunning/SaveCompleted） | 子代理运行记录独立落盘按会话归属 | **子代理自身的断点续跑不归本件**（已有独立机制，边界见 §8） |
| desktop hub 拉推合流（workflow_runs_app.go） | `workflow:runs` 运行时事件推送 + 面板打开 `WorkflowRunsSnapshot()` 全量拉取；250ms 合并窗口 | 「可续跑」状态走同一通道，不加第二推送面 |

### 1.4 对照结论

1. **竞品有真机制可对照，不是发明新机制**：zcode 的「快照覆盖写 + 节点终态保留 / active 重置重跑 + 独立 resume 入口 + 溯源属性」是完整先例，fork 的设计逐点有对照。
2. **fork 不需要 zcode 的事件 journal 半轨**：zcode 文件型同时维护 events.jsonl 追加流与 run.json 快照，是因为它要跨进程重放观测流；fork 的节点六态事件流已有 UI 实时通道（recordingSink → 发起会话 sink → workflow:runs 推送），持久化只需服务「重启后状态恢复」一个目的——**快照覆盖写单轨即可**，少一套 journal 一致面。
3. **fork 不需要 SQLite**：zcode 的 dwf journal 服务高频多 run 的内省查询（ListRunsByParentSession 等）；fork run 频率低（每天个位数~几十）、单 run 快照小（见 §3 体量估算），目录枚举 + JSON 文件与既有 store.go 完全同构，无查询面需求。

## 二、run 状态落盘设计（存储形态）

### 2.1 选型：WorkflowsDir 侧车（结论先行）

**选 `<WorkflowsDir>/runs/` 侧车，不选 sessions 侧车。** 判据：

| 判据 | WorkflowsDir 侧车 | sessions 侧车 |
|---|---|---|
| 归属语义 | run 是**应用级面**：686 面板是应用级视图、定义是应用级目录、任何工作区会话可见（store.go 注释明示「应用级目录而非工作区目录——任何工作区的会话定义的工作流都互相可见」） | run 挂进发起会话目录后被单会话私有化；会话删除/清理 = run 历史陪葬，与面板应用级语义冲突 |
| 数据源一致性 | 面板 Snapshot / workflow_status / 磁盘历史同一目录收口（定义与运行同处） | 面板要跨「全部会话目录」聚合才能拼出应用级 run 列表——每次快照扫 `AllProjectSessionDirs()`，成本与复杂度都错 |
| 既有一致先例 | heartbeat run-history sidecar 同为「应用级状态根 + 侧车文件」；定义存储已在同一目录 | 无先例：会话目录目前只装 transcript/转录，没有「应用级运行登记」挂会话的先例 |
| resume 发起方 | 任意会话可续任意 interrupted run（面板按钮与工具都应用级） | 天然变成「只有发起会话能续」，跨会话续跑要跨目录搬运 |

jobs.SessionFromContext 的「发起会话」语义保留不变——它继续管**事件流与子代理转录归属**（嵌进发起者事件流、转录记发起者名下），不因存储选型改变；run 本体的登记面在 WorkflowsDir。

### 2.2 目录与文件布局

```
<WorkflowsDir>/
├── <slug>.json                 # 既有：定义（不动）
└── runs/
    └── <runID>/
        └── run.json            # 该 run 的最新快照（唯一文件，快照覆盖写）
```

- **一个 run 一个目录一个文件**：runID（`wf-<hex12>`）已是唯一键且字符面安全（hex），直接作目录名；slug 逃逸问题不存在。
- **写入时机（天然钩子）**：`Service.recordNode` 已是每次节点事件到达的收口点。节点到达**终态**（completed/gate_passed/failed/unconfirmed/skipped 判定）时增量重写 run.json——`fileutil.AtomicWriteFile` 原子覆盖写。写盘失败只 `log.Printf` 降级不阻断运行（持久化是增强不是门禁：写不了盘的极端环境 run 照跑，只是不可续）。
- **run 级终态**：`finishRun` 落终态时最后写一次（State=completed/failed + EndedAt + Report）。cancelled 落 `failed("cancelled")`（既有语义不动），可续跑标记见 §4.3。
- **schemaVersion 前向保护**（继承 heartbeat sidecar 语义）：快照带 `schemaVersion`，读到高于本二进制认识的版本 → 跳过该 run 的恢复并在面板标「需要新版本 Reasonix 才能续跑」，绝不覆盖写坏未来格式。
- **损坏文件语义**（继承 store.list）：枚举时解析失败的 run.json 跳过不炸启动，log 提示。
- **极端环境**：WorkflowsDir 解析为空（既有 store 的 dir="" 分支）→ 不落盘，resume 整体不可用但运行行为与今天逐字节相同。
- **体量估算**（推演，供裁决）：审计类 workflow 典型 10-30 节点；单节点 output 截断 64KB（§3.3）后单快照 ≤ 2MB，100 条上限（§7）封顶 ~200MB 磁盘，实际远小（多数节点 output 是结论摘要不是全文）。

### 2.3 快照 JSON 形态（草案）

```jsonc
{
  "schemaVersion": 1,
  "runId": "wf-5df7bc97bf7a",
  "workflow": "audit-line-batch",
  "defFingerprint": "sha256:<name|schemaVersion|nodes 序列化|edges 序列化>",   // §4.4 定义漂移校验
  "state": "running",                    // running | completed | failed；重启后服务侧派生 interrupted（§4.2）
  "startedAt": "2026-11-01T09:00:00Z",
  "endedAt": null,
  "err": "",
  "cancelled": false,
  "phase": "审计执行",
  "failedNode": "",
  "gateRound": 0,
  "nodes": {
    "<nodeID>": {
      "nodeType": "subagent",
      "status": "done",                  // 引擎 nodeStatus 序列化：done | skipped | aborted
      "terminal": "passed",              // passed | gate_failed | skipped
      "gatePassed": true,                // 仅 gate 节点有意义
      "round": 2,                        // 门重试轮次
      "detail": "exit 0",
      "output": "<interpolatable 输出，≤64KB，超限截断+truncated 标记>",
      "outputTruncated": false,
      "result": { },                     // typed result / join map（JSON 值）
      "findings": [ ]                    // 该 producer 节点的 findings（promotion 用）
    }
  },
  "bag": { "findings": [ ] },            // reportBag 全量（where/what/evidence/status/severity）
  "verifs": [ "go test ./... (exit 0)" ],
  "report": null                          // 终态时落 WorkflowReport
}
```

字段与引擎 `runState` 一一对应（engine.go:78-88），恢复时直接灌回，不需要引擎新增第二种状态表述——**快照 schema 就是 runState 的序列化投影，单一语义一份真相**。

## 三、节点级 checkpoint 设计（checkpoint 粒度）

### 3.1 粒度裁决：节点终态为 checkpoint 点

- **checkpoint 点 = 节点到达终态的一刻**（execute.go 中 `finish()` 与 abort 两类出口 + skip 判定），由服务侧 `recordNode` 钩子统一捕获，引擎自身不感知磁盘。
- **running 中的节点不落中间态**：运行到一半的节点没有可恢复语义（子代理的中间进度已有转录侧车承载；gate 命令原子性天然无法拆）。
- **恢复规则直接对齐 zcode reconcile 语义**：
  - 快照里 `status ∈ {done, skipped}` 的节点 → 恢复为已完成（stDone/stSkipped + terminal + edge 决策重放），**不重跑、不重复烧子代理 token**；
  - 快照里 running 中（无终态记录）或 aborted 的节点 → 重置 pending，resume 后重跑；
  - fixer 节点不落快照（它只在门循环内跑，恢复门节点即恢复整个循环从 round 1 起——门循环重跑代价是一次 shell 命令 + 可能的 fixer 调用，可接受；快照记 gateRound 仅用于报告展示）。

### 3.2 边决策重放

恢复时按快照重放 `resolveOutEdges`：每个已完成节点的 terminal + gatePassed 足以重建 `schedEdge.decided/active`（engine.go:253-268 的决策是纯函数），下游 `inState` 判定随即与原 run 一致。confirm 的隐式 target→confirm 边同样由 newRunState 重建后按 target 状态重放。

### 3.3 output 截断与不可恢复节点

- 单节点 `output` 超过 64KB 截断存尾（与引擎 emit 的 truncate 240 字符口径不同用途：快照 output 服务 interpolate 与 confirm evidence，取**尾部**与 gate 输出习惯一致）；
- `outputTruncated=true` 的节点在 resume 时**整节点重置重跑**（它的下游 interpolate 会拼出残缺 prompt）——宁可重跑不可续错。join 节点的 `result` 是聚合 map，体积小，不设截断。
- 粒度不做更细（节点内步骤级）：fork 节点执行体是「一次子代理调用 / 一次 shell 命令」，天然原子；更细粒度是 zcode scheduler collection 那种开放图才需要的能力，fork DAG 用不上（YAGNI，且竞品节点级也停在 active/pending 二分重置）。

## 四、resume 入口与恢复语义

### 4.1 三层入口

| 层 | 入口 | 形态 |
|---|---|---|
| 引擎 | `Engine.ResumeWithID(ctx, wf, snap)` | 新增方法：从快照重建 runState（灌回 status/term/gatePassed/output/result/findings/bag/verifs/phase/failedNode）→ 重放边决策 → 复用既有 `runAll` 调度器继续（已终态节点非 pending，扫描自然跳过——调度器零改动） |
| 服务/工具 | `workflow_run` 增可选参数 `resume_run_id` | **推荐**：不新增工具面；`workflow_run(name, resume_run_id="wf-…")` = 从该 run 快照续跑。备选（独立 `workflow_resume` 工具）语义等价但多一个工具名，不推荐 |
| 面板 | 运行列表行「续跑」按钮 → `App.WorkflowResumeRun(runID)`（Wails 绑定） | 与既有 `WorkflowCancelRun` 同款形态（desktop/workflow_runs_app.go 尾部已留此模式） |

### 4.2 重启恢复与 interrupted 态

- `RunState` 增一态 **`interrupted`**：进程重启后从磁盘恢复的、快照 state=running 的 run。三态语义变为：running（本进程活跑）/ completed / failed / **interrupted（可续跑）**。cancelled 仍落 failed("cancelled")，见 4.3。
- **启动恢复**：`Global()` 首次构造后异步扫描 `runs/` 目录（与定义 store.list 同款枚举），终态 run 载入只读视图（面板历史不再因重启清零——顺带修掉「重启后面板运行列表全空」的次生缺口）；interrupted run 标可续跑。磁盘为权威、内存 map 为缓存。
- 快照 state=running 且 `endedAt` 为零 → interrupted；不尝试判断「进程是不是崩溃」——凡本进程没有 finishRun 落袋的一律 interrupted，语义简单且保守（正确：既然没落终态就有未完工作）。

### 4.3 哪些 run 可续（可续跑判定，服务侧单一函数）

```
resumable = (state == interrupted)
          && 定义仍存在（store.load 成功）
          && defFingerprint 匹配（4.4）
          && !cancelled
```

- **cancelled 不可续**（对齐 zcode「user stopped on purpose, do not resume」）：用户点停止 = 主动放弃，自动给它挂「可续跑」是违背用户意图的面板噪音。想继续就重新 workflow_run（成本：重跑，接受）。
- failed（真实失败，如门循环耗尽且无 fail 分支接收）**可续**：失败现场正是断点续跑的主用例——修复环境后续跑，已完成节点不重跑。这是对 zcode「errored 走 AmendWorkflow 改脚本」的 fork 式简化：fork 不支持 run 间改脚本（定义是独立落盘的，改定义走 workflow_define overwrite），失败 run 续跑直接对同一定义。

### 4.4 定义漂移防护

resume 时 load 定义并重算 fingerprint（`sha256(name + schemaVersion + nodes 序列化 + edges 序列化)`，canonical JSON 保证稳定），与快照比对：不匹配 → 拒绝续跑，报错文案给已存在的下一步：「workflow X 已被修改，与该 run 的断点不匹配；重新 workflow_run 从头跑，或 workflow_get 查看当前定义」。**禁止拿旧断点配新图**——边决策重放的前提是同构图。

### 4.5 续跑的会话归属（显式取舍）

- 续跑按**发起续跑的会话**解析 RunnerSource 与 sink（既有 boot 注册面不变）：事件流嵌进续跑发起者的会话、子代理转录按 `agent.WithParentSession` 记续跑发起会话名下。
- 取舍说明：原发起会话可能已关（审计线跨重启场景正是如此）；「续跑是新会话接管」比「试图 resurrect 旧会话事件流」简单且不造新机制。代价是事件流换了会话——面板 DAG 视图不受影响（workflow:runs 是应用级通道），只有发起会话的 feed 里有节点事件。
- resume 的 runCtx 同样 `context.WithCancel(context.Background())` 自有生命周期（跨 turn 存活），cancel 链路与 RunWorkflow 同构。

### 4.6 引擎改动面清单（候裁决后实现件的范围）

1. `internal/workflow/persist.go`（新）：快照 marshal/unmarshal、fingerprint、runs 目录枚举与 prune（§7）、`fileutil.AtomicWriteFile` 封装；

## 六、tl1324 联动：观测面评估说明（jobs.Manager 登记 vs 面板子代理视图）

### 6.1 现状三面（证据链）

| 观测面 | 承载机制 | workflow 现状 |
|---|---|---|
| jobs.Manager（后台 job 胶囊；wait/kill/bash_output 工具承接） | `task.go:959-999`：task 工具 `run_in_background=true` 时 `jm.StartForSession(...,"task",...)` 登记 | **不进**。workflow 的 `runCtx` 从 `context.Background()` 派生（service.go:203），只挂 WithParentSession/WithSession，不挂 WithManager → `jobs.FromContext` 不命中；且 SubagentRequest 不带 run_in_background，子代理走前台同步路径 |
| desktop 前台子代理视图（foreground-subagent registry，task 557） | `emitSubagentLifecycle`（subagent_outcome.go:222）→ `event.RecordSubagentLifecycle` → desktop/metrics_app.go 消费；`backgroundOwnedKey`（subagent_lifecycle_scope.go）阻止 job-owned 子代理双计 | **进**。workflow 子代理走前台路径 → background=false → lifecycle 事件进 registry（面板子代理视图可见每个节点子代理） |
| workflow 自有面（workflow:runs 推送 + workflow_status 工具 + 686 面板） | `Service.s.runs` 内存登记 → recordingSink 更新 → hub 250ms 合并推送 | run 级状态唯一落点，但纯内存——**本件持久化后此面成为 run 的权威观测面** |

### 6.2 候设计结论（1324 的输入）

1. **workflow run 不应登记进 jobs.Manager**。判据是生命周期不同源：jobs 面语义 = 「某会话内、跨 turn 的后台 job，由 wait/kill 工具承接、胶囊 UI 呈现」，job 与会话共存亡；workflow run = 跨会话、跨重启、应用级，观测已由自有面（workflow:runs + workflow_status + 面板）完整承载。把 run 塞进 jobs 面需要给 jobs 引入「无 wait 工具承接的应用级 job」这一新物种——违反「先用现有机制」且无消费方（没有任何工具需要 wait 一个 workflow run；面板已有停止钮）。
2. **子代理级观测维持现状**：workflow 子代理走前台 lifecycle 语义随发起会话走（resume 后随续跑发起会话走，§4.5）——registry 天然跟随，无需新机制。1316 的持久化只落 run 级（workflow 自有面 + WorkflowsDir），不触碰两个子代理观测面。
3. **1324 需另评的剩余面**（不在本件范围，供其收口）：① fleet/并行子代理在 workflow 里的表现（fork 引擎是顺序调度器，无并行，暂无面）；② jobs 面若未来要「会话内可见本会话发起的 workflow run」聚合视图，应做成 jobs 侧只读投影而非登记（结论方向性，候 1324 裁决）。

## 七、service.go:219 运行记录回收上限（tl1323 核实遗留收口）

### 7.1 现状（tl1323 结论复核确认）

- `service.go:218-219` 是唯一写入点（`s.runs[runID] = rec` + `s.order = append`）；全文件 `delete/remove/prune` 零命中——**每次 RunWorkflow 永久 +1，进程生命周期内只增不减**。
- RunRecord 持有 `def *Workflow`（整图）、`nodes map`（每节点六态记录）、`Report *WorkflowReport`（含全部 findings 原文）——审计类批跑（一条 run 几十个 findings + 大 answer output）单条可达 MB 级。桌面进程挂机数天 + 批跑场景内存缓涨无界。
- `WorkflowStatus` 的「截 20 条」只是**视图**截断，登记不裁；`Snapshot()` 每次锁全序遍历，列表越长面板推送越重。

### 7.2 设计：终态 run 保留窗口上限（与磁盘侧车同一边界）

- **常量**：`workflowMaxFinishedRuns = 100`（终态 run 内存+磁盘同步保留的条数）。量级依据：heartbeat `maxRunHistory=20` 是 per-task 的低频心跳历史；workflow run 是全局低频重件（每条含报告），100 条 ≈ 数周批跑窗口，面板与 workflow_status 的 20 条视图截断仍在窗口内，够用且封顶 ~200MB 磁盘（§2.2 估算）。
- **逐出规则**：只有 `state ∈ {completed, failed}` 的 run 可逐出；**running 与 interrupted 永不逐出**（它们是活工作或待续工作，逐出 = 丢断点）。取消语义的 failed("cancelled") 同为终态可逐出。
- **触发点**：① `finishRun` 落终态后惰性 prune（新终态入列，从最老终态开始逐出超额行）；② 启动恢复扫盘后 prune 一次（清理历史积压）。
- **内存与磁盘同步逐出**（单一边界，不搞「内存裁了磁盘留着」的两层真相）：逐出 = 删 `runs/<runID>/` 目录 + 删 map/order 行，先磁盘后内存，失败降级 log。
- **面板/工具影响**：被逐出 run 从 workflow_status 与面板消失——这是语义不是 bug：100 条窗口外的 run 视为「已归档出列」。workflow_status 的报错文案已有「unknown run; call without run_id to list recent runs」，窗口语义与其自洽。
- **此件实现归属**：与 1316 主体同件落地（回收上限天然依赖「终态可判定 + prune 钩子」，独立做要在 finishRun 单独立钩子，两件并做只写一次）；tl1323 的 tasklist 在本设计落地时以实现件为准收口。

## 八、验收矩阵（实现件的验收标准先行）

| # | 场景 | 预期 |
|---|---|---|
| 1 | define→run→kill 进程→重启 | 面板见该 run `interrupted` + 「可续跑」徽章；已完成节点显示终态；无 finishRun 的 running 中节点重置 pending |
| 2 | 续跑断点 | `workflow_run(resume_run_id=…)` 从首个未决节点继续；已完成节点**不重跑**（子代理零重复调用，可用节点事件序/子代理转录计数断言） |
| 3 | resume 时定义已被 overwrite | 指纹不匹配 → 拒绝，报错含「重新 workflow_run / workflow_get」两个已存在下一步 |
| 4 | completed / failed(真实失败) / failed("cancelled") / interrupted 四态逐一 resume | completed 拒绝（无可续）；真实失败可续；cancelled 拒绝；interrupted 可续 |
| 5 | gate pass 分支已决后中断，resume | pass 边保持 active、fail 边保持 inactive（边决策重放正确，下游不跑错分支） |
| 6 | target 完成 + findings 已落袋后中断，confirm 未跑，resume | confirm 直接可跑，evidence 取自快照 output/result；promote 语义不变（unconfirmed→verified 原地升级） |
| 7 | join 上游已完成，resume | join 聚合从快照 output/result 重建，interpolate 输出与不断版一致 |
| 8 | 单节点 output 超 64KB 后中断，resume | 该节点重置重跑（outputTruncated 语义），下游拿完整输出 |
| 9 | 回收上限 | 第 101 条终态落袋后最老终态 run 磁盘目录与内存行同步消失；构造 running/interrupted 各 1 条 + 100 条终态 → 两条未完 run 不被逐出 |
| 10 | 损坏 run.json（手改坏） | 启动扫描跳过该 run、log 提示、其余 run 正常恢复（store.list 同款语义） |

| 12 | WorkflowsDir 解析为空 | 行为与今天逐字节相同（不落盘不恢复），run 正常执行 |

## 九、通俗版一句话

工作流跑到一半重启就全白干，因为账本只记在脑子里（内存）；本设计给它配一个写在硬盘上的记账本——每干完一个节点就更新一次账本，重启后翻开账本接着干，干过的不重干；顺手给账本加了「最多留 100 页」的规矩，防止本子越记越厚把书包撑破。
