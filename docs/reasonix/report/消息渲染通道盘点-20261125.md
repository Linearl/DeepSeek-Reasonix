## 0. 结论先行（四选一）

**消息渲染通道准入机制 = 必需，且应以「归一化单一准入闸」立项（P1 候），草案见 §6，本件不实施。**

四选一判据：

1. **为什么不是「冗余可删」**：写入者是多端/多通道产品形态固有的（切 tab、切端点、重启恢复、引导注入、压缩、投递恢复都是真场景），删任何一个写入者都丢能力。
2. **为什么不是「有用但可简化」就够**：2026-10 至 11 双绘/重入/漏渲染同族已修 ≥7 件（§4），每一件都是「两个写入者世代判定不一致」的单点补丁；tl1739 一件两轮返修后触发源仍在扩大（pending 在案）。单点补丁模式已被实证收敛不了——「简化现有散键」与「补下一个单点」无法区分。
3. **为什么是「必需」而非「无法判定」**：8 种世代键（§3.1）全部已存在于代码中，归一化不是发明新机制，是把既有键收拢到单一判定点（符合「先用现有机制」设计原则与宪法判据）；且协调线三层结构读码结论经本轮逐行核实成立（§2）。
4. **风险对冲**：准入闸只收拢「数据装配层」判定键；渲染面 5 组件、TranscriptStore 缓存策略、kernel（滚动侧世代）均不动（non-goals），退路=闸是 reducer 内纯函数守卫，删除即回原状。

## 5. 复发机制定性（为什么反复修仍复发）

1. **判定键没有归一**：同一对写入者（如 W1×W2）的先后到达序要靠 K3+K5（W1 侧）和 K4+K5（W2 侧）两套键各自判一次，两边对「同一行是否已在表面」没有共享答案。
2. **每个新触发面=一对新的写入者交错**：切 2 tab（W1×W2 交错窗）、切端点（W2 换 endpoint → epoch 翻代 × W2 自身）、回合结束切 tab（W1 收尾 × W2 重入）、重启注入（W5/账本 × W2）——矩阵里每换一行列组合就是一个新 bug。
3. **修法都在「加一条对角线外的判定」**：1712 加文本折叠、1739r1 加 floor+指纹门、1739r2 加 turn-id 去重——每件都正确，但都在给矩阵打补丁而非给矩阵降维。
4. **数据层 543 先例证明归一是可行的**：重入族在 Go 数据层做了幂等键统一后前端零复发；渲染装配层至今没有等价动作。

## 6. 路线草案：归一化单一准入闸（surfaceAdmission，仅草案，本件不实施）

### 6.1 闸位置（一级提案：reducer 顶部统一守卫段，非新层）

- 新建 `desktop/frontend/src/lib/surfaceAdmission.ts` 纯函数模块；**不改 reducer 结构、不加新 action、不加新层**——把现在散在 4 处的准入判定收拢为单一入口：

```ts
// 伪签名（草案）
admitSurfaceWrite(state, write): { admit: boolean; reason?: string }
// write 携带: writer: "live"|"hydrate"|"compaction"|"inbox"|"optimistic"
//           键: { sessionGeneration?, revision?, digest?, eventSeq?, inboxItemId?, submissionId?, turnId? }
```

- reducer 各 case 首行改调 `admitSurfaceWrite`（event/stream_batch/history_replace/rebase/prepend/guidance_bubble/user 七个 case）；`historyRevisionIsOlder`、657 水位线、guidance_bubble 的 inboxItemId 去重、1712 文本折叠的「判定部分」全部内迁为该模块的子判定（渲染动作如折叠、并集保留仍在原 case，只收判定）。
- W1 的 fence（askPanelGate.judgePromptFenceArrival）与投影器（turnEventProjection）保持现状——它们是「事件准入门」，本闸是「落面准入闸」，两层各司其职；闸只接管 reducer 侧的落位判定（含 1739r2 的 turn-id 去重从 handleWireEvent 内迁，投影器游标推进语义不变）。

### 6.2 统一键设计（不发明新键，只定派生规则）

- **行身份 SSOT = K5（entryId 派生稳定 id / turnStableIdentity）**：闸内维护 per-tab `renderedTurnRows: Map<turnId, count>` 与 `renderedItemIds: Set<itemId>`，随 reducer 落位增量维护（append+1 / replace 重建 / reset 清空）——1739r2 的扫描升级为 O(1) 查表。
- **表面世代 SSOT = (sessionGeneration, revisionBand, appliedEventSeq) 三元组**，其中 revisionBand = 现有 historyRevisionIsOlder 语义原样搬入。**不落盘、不新增后端字段**（从现有 meta/状态派生，不建第三真相源）。
- 每个写入者接入表（闸的判定矩阵代码化，与 §3.2 一一对应）：

| writer | 闸内判定（从现状内迁） |
|---|---|
| live | appliedEventSeq 水位线（657）+ renderedTurnRows 查表（1739r2 内迁） |

## 7. 通俗版

把聊天记录的显示区想象成一块白板，五个人都能往上写字：直播员（打字机式的实时输出）、档案员（切标签页/换端点时从磁盘把历史铺回去）、压缩员（把旧对话折叠成一张卡）、信使（把引导消息插成气泡）、乐观员（你按回车的瞬间先把你那行写上去）。五个人各有一套「该不该我写」的暗号：直播员看序号连不连续，档案员看版本号对不对，信使只认消息编号，乐观员什么都不看先写了再说，压缩员只看自己那张卡。

过去一年修的七八个「字写了两次/该写的没写」的 bug，全都是同一类事故：**两个人用了不同的暗号，各自以为对方不会写，结果撞了或者都让了**。每回修法都是给撞车的那一对补一句「你俩对一下这个暗号」——下一对人再撞，再补。这不是哪个人粗心，是暗号制度本身散装。

盘点的结论：这套多写白板必须有一个统一门卫——任何人下笔前先到同一个窗口登记「我是谁、我的版本号、我要写的行在不在板上」，窗口用五个人已有的暗号做判定，不发新暗号、不改白板材质、不动档案室的货架。数据层的老任务 543 当年就是这么根治的（统一幂等键后前端再没复发），渲染层一直没做这一步。建议先让在飞的 1739 返修落地，然后立一个独立任务做这扇门卫窗口；草案在 §6，过目后才动工。
