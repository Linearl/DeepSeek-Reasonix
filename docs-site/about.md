# 关于本 fork

本仓库是 [esengine/DeepSeek-Reasonix](https://github.com/esengine/DeepSeek-Reasonix) 的长期维护 fork（`Linearl/DeepSeek-Reasonix`，主线 `main-v2-stable`）。数据与上游兼容，随时可切回官方版安装包。以下六节说明：我们遇到了什么、怎么开发、保留与放弃哪些机制、版本怎么编、维护现状与后续计划。

## 一、上游的高频问题

我们日常重度使用上游，也向上游提交过 issue 与 PR。反复撞到的问题集中在几类，其中一类是**机制性的**：

### 点名：未遵循 SSOT（单一事实源）原则

同一个语义在代码里存在两份以上互相独立的事实源，其中一份改了另一份没跟——这类问题在上游反复出现，且症状往往是「静默失效」而非报错，用户很难自查。我们在使用中撞到的实例：

- **切模型导致上下文暴涨**：投影有效性被绑在含模型标识的缓存键上，切一次模型整份投影作废、可见视图回退全量，上下文占用可从 10% 涨到 77%。
- **同一开关两处声明**：某实验特性在设置面板的注册表与内置默认表分属两处，改一处不生效；我们为此给实验室布局立了「yaml 必须与内置默认同构，任何一行不合规则整份作废回退安全网」的硬约束。
- **档位标记与实际范围脱节**：稳定性档位标了「已稳定」，但真正参与判定的 ID 集合是空的，导致该档位恒不生效且不产生任何告警。

我们的做法是：**能收成一处的绝不留两处**；必须两处时，用测试锚点把它们锁在一起，任何一侧改动都会让门禁变红。

### 用户报告的高频痛点（我们已解的）

以下问题在上游 issue 区反复出现，我们在 fork 内做了对应治理：

| 上游现象 | 我们的处置 |
| --- | --- |
| 压缩阈值爆表后被告知「剩 0 空间」 | 压缩失败保留部分进度、失败原因三态显性化、可指定压缩模型 |
| 压缩提示读起来像报错、吓人 | 压缩可观测性：进度可见、分阶段文案与预期时长 |
| 点停止后审批卡死、新指令被拒 | 停止按钮三级（普通→升级→强制）+ steer 队列治理 |
| 后台任务静默失败、activity 里看不见 | 完成自动叫醒会话 + 失败可见 + 一键重发 |
| 执行中异常自动中断 | 中断恢复族：幽灵运行态根治、打断后只读命令直接重跑 |
| 会话异常退出后卡「运行中」、新消息被吞 | 自愈桥 + 卡死形态检测 + 可见打点 |

完整差异台账见仓库 [`release-notes/FORK-vs-upstream.md`](https://github.com/Linearl/DeepSeek-Reasonix/blob/main-v2-stable/release-notes/FORK-vs-upstream.md)。

## 二、开发方法论

### 标杆学习（四条）

1. **竞品先行**：动手前先看同类产品怎么做。设计新机制前必做竞品调研——问三件事：竞品怎么做、我们分叉的收益证据是什么、保留成本是多少。没有竞品对照的新机制默认高危。
2. **反复返修模块溯源**：同一个模块在短时间内被反复返修，说明前面几轮都在打补丁而不是治根。此时停止加补丁，回溯根因并问一句：这个机制是不是本身就不该存在？
3. **实验开关落地**：任何新能力一律挂实验开关，默认关闭且关闭时行为与引入前逐字节一致。这样新特性可以独立开关验证、随时回退，不必用回滚整个提交来止损。
4. **多 agent 协作分工**：主对话负责编排与验收，执行线在独立 worktree 内开发，交付以回板与门禁读数为准，而非口头自报。

### 高质量反馈体系

反馈不是「提了就完事」，而是要能被复现、被定位、被验证。我们沉淀了三层：

- **技能化**：把反馈的写法、诊断的入口、复现的步骤写成可复用技能，让任何人（包括 agent）提反馈时都走同一条最短路径。
- **日志化**：关键路径都有可检索的日志打点；错误只被包装返回而不落日志的「静默通道」是重点整治对象——无日志不等于未发生。
- **内置反馈机制**：应用内提供卡顿与崩溃的一键分析入口，把「用户遇到问题 → 描述 → 截图 → 猜测」压缩成一次点击；分析会话统一归档，进度实时可见。

### Agent 也是环境的使用者

过去我们只把 agent 当执行者，忽略了一点：**agent 同样是这套工具的用户**，它也会踩坑、也会有话要说。

- 让 agent 能反馈问题（工具报错时给出正确用法与自愈建议、能力调用失败时引导到正确用法），对改善工具列表的用处非常大——因为 agent 会在一次会话里高频调用工具，它是最快的回归测试。
- 反过来，agent 的反馈也是可观测资产：一天内哪些工具反复报错、哪些报错后 agent 自纠成功，直接指向下一轮该修什么。

## 三、fork 增强与取舍清单

保留什么、放弃什么，依据是「我们的真实需求」而非「上游做了什么」。上游新增不等于我们要跟，上游删除也不等于我们要删。

| 上游机制 | 我们的处置 | 理由 |
| --- | --- | --- |
| DAG 全量回放 | **已退役** | 全量回放的成本随会话规模线性增长，而收益只在极少数诊断场景可见。退役时先做存量一次性无损迁移（每个文件留备份侧车，可单文件回滚），再把读侧收敛到单一路径——消除「同一语义两个真相源」的隐患。 |
| 回退全量投影 | **改为有界处理** | 投影失效时整轮全量重投影，在超大长会话上表现为数十秒卡顿甚至超窗失败。改为有界处理 + 自愈，不再整轮重投影。 |
| recovery fence | **不采用** | 该机制系从上游继承而非自研，且上游 studio 侧已弃用。保留只会多一层需要维护的状态。 |
| 存储版本 v4/v5 | **推荐 v3** | v3 为长期推荐档；v4 可用但 v3 侧记录会滞后；v5 是上游新引入的方向，稳定性未经我们验证。提供 v4→v3 迁移器（带备份提醒与进度可视化）。 |
| write gate 契约门禁 | **已移除** | 门禁拦的是 AI 的写操作，误拦成本高于收益。移除后写操作不再被契约门禁拦截。 |

## 四、版本编号规则

- **正式 Release** 发布到 GitHub Releases，可从 Release 页直接下载安装。
- **内部包** 在基线版本号后追加出包时刻的时间戳（`1.38.3-YYYYMMDD-HHMM`，精确到分钟）。这样做的原因很实际：我们一天可能出多个包，不带时间戳就无法区分它们；而版本号本身**不自增**——版本号跟随上游基线，不随我们出包次数递增，避免制造「我们已经到 1.50 了」的错觉。
- 每个包都必须在出包台账留档；release notes 以「基线 = 上一个发布的版本」写增量。

时间线与每个包的改动见[更新日志](../changelog/)。

## 五、维护现状

自 `1.38.3-20261009` 基线起，本 fork 进入**独立演进**状态：不再以追齐上游版本为优先目标，bug fix 的 cherry-pick 仍然保留，向上游反馈 issue 与 PR 的通道也仍然开放。

需要说明的是：`1.38.3-20261009` 及其后的时间戳包都是**内部构建版本**，并未作为 GitHub Release 发布；正式 Release 与内部包的区分见[更新日志](../changelog/)页首说明。

「独立演进」不等于「分叉即断」——我们的数据目录与上游完全兼容，随时可以覆盖安装官方版继续用。

## 六、路线图

- **短期**：稳定性与可用性持续还债——压缩、上下文预算、会话存储三块的体验与可观测性。
- **中期**：多 agent 协作体验（协作中心、子代理面板、群聊）走向成熟；工作流编排从实验特性转正。
- **长期**：让长时间自治运行始终「可读、可撤销」——这是本 fork 立项的初衷。

进度与计划以仓库 issue 区与[更新日志](../changelog/)为准。
